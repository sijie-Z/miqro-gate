## 1. 泛化兜底会藏起真实类别（CI/构建两例）

与 Runbook §15.2 同一个形状：**症状指向错误的层**，真信号在层外。

| 症状 | 看起来像 | 真实原因 | 去哪里找信号 |
|---|---|---|---|
| CI Java 单元 job **30–45s 速挂** | 代码坏了 | Spotless 下载 Eclipse JDT formatter 网络超时（`SocketTimeoutException`），与代码无关 | **失败耗时形态**（速挂 ≠ 测试真的跑了）+ 日志关键词；冷却 10 分钟 rerun |
| 构建**静默卡死** | 编译本来就慢 | Maven 依赖下载挂起（到 CDN 的 ESTABLISHED 连接零数据） | **CPU 时间增长**（停滞 = 卡死，而不是看日志）；kill 重试——实测 10 分钟 CPU 只涨 23 秒，kill 后重试 4 分钟建完 |
| 请求带 `Accept: application/x-yaml` → **500** problem+json | 服务端内部错误 | `HttpMediaTypeNotAcceptableException`（无 YAML 序列化器）被兜底映射为 500——**本应是 406**；fail-closed、无数据泄漏 | 看**响应体**（problem+json 带 `code`）与异常类型，别只看状态码（同族：409 要看 `code` 不看状态码） |

2026-09-18 真机补充：卡死的构建会**持有部署锁**（flock 阻塞全线）；判别仍用 CPU 时间，
处置是终止卡死进程让锁释放——等待方的部署会接管。

2026-09-21 补充第三例（#1088 收尾批复核发现）：见上表末行——"不该给的东西给不出（406）"
被兜底成了"出错了（500）"，症状仍指向错误的层。

## 2. 「全绿」≠「验过」：先证明红灯会亮（测试方法两例）

| 现象 | 看起来像 | 真实原因 | 行动点 |
|---|---|---|---|
| 单跑绿、全量红 | 本用例有 bug | 共享单例状态被别的用例改过（Spring 上下文单例的熔断桶停在 OPEN，首个断言拿到 503 而非预期状态码） | 「你碰了不属于你的状态」：先查单例/静态/共享上下文；给测点留复位 seam（`reset()` + `@BeforeEach`） |
| 长期绿、其实什么都没测 | 「历史不动」已被验证 | 比较两边恒等：fixture 的随机 `project_id` 被 summary 的 `projects` JOIN 丢掉 → 成本恒为 0，断言在比较 `0 == 0` | 比较型断言必须自带「**基线非零**」前置；再用独立精确值断言兜底（`expected 0.002 but was 0` 才是暴露它的那条） |
| 新加的集成测试跑过后，**其后 8 个类 36 例齐红**（`expected:<201> but was:<401>`） | 装配顺序/过滤器链回归，或环境抖动 | **共享测试容器里的跨类残留**：新测试 `setUp` bootstrap 出的管理员+探针数据未清理 → 后续类 bootstrap 得 401（already bootstrapped）；残留行数是铁证（`expected: 1L but was: 3L`） | **谁 bootstrap 谁清理**（`@AfterEach` 复位共享库，照 `AdminOrgApiIntegrationTest` 既有约定）；新集成类须给出「跑完不影响后续类」的证据；**"失败清单 = 污染源之后执行的类"就是共享容器残留的指纹**（2026-09-21 #1088 收尾批实测） |

共用行动点：**新回归测试收工前先证明"它会红"**——把被测点改坏（或造出非零基线），确认断言真的
变红，再相信绿灯。同族先例 #754（CSV 表头错位近一年未被 `contains()` 式断言抓到）。

**2026-09-18 把这句从"一次性动作"升级成"常设闸门"**：`deploy/tests/deploy_script_regression.py`
（CI job `Deploy script (behavioural)`，见 #818/#819）**每个场景只造一个缺陷**再问脚本能否发现——
**在健康栈上通过不算证据，要在坏栈上失败才算**；三条部署断言的修复各自做过反向验证
（改回坏实现 → 10/12、11/12、10/12 如期红）。

## 3. 读源码要读**已合并的 revision**（工作树会停在旧 commit）

- **现象**：核查"新加的 `quote()` 有没有接线"时，得出"定义了却从未被调用"——**差点发出一条假发现**。
- **真实原因**：读的是**工作树里的文件**，它停在旧 commit；合并后的版本里 `join()` 早已改为逐格 `quote(v)`。
- **行动点**：判断"某改动是否生效/接线"一律用 `git show origin/<branch>:<path>`（或 PR 的 merge
  commit）；工作树只用于**编辑**，不作为事实源。与 §15.3 同族：**"我看到的源码"也是输入**，
  同样适用"别把没验证的输入当事实"。

## 4. 「缺口」判断先查权威表述（"没接线" ≠ "没承诺接线"）

- **现象**：看到 `deploy/backup/test-*.sh` 没有任何 workflow 引用 → 判"承诺了测试但没接线"。
- **真实原因**：runbook 写的就是**季度人工演练**，承诺不存在；真瑕疵只是"已验证 PASS"的措辞
  容易被读成"每次提交都会跑"（已在该表格下补注澄清）。
- **行动点**：判缺口前先查权威表述（文档/issue/ADR），避免为一个不存在的失约去加一条没人要的 CI。

## 5. 「没牙的检查」与「误报的检查」

同一枚硬币的两面，共同后果都是**"这条检查到底证明了什么"失效**：

- **没牙的检查比没有检查更坏**——它会被当成有牙的：部署冒烟一度只打门户根（不经过 Origin 校验）
  且对 `000` 只告警，于是配置全丢的容器被"deployed and verified"放行（#805 事故链）。
- **误报的检查会被无视**——它比被检查的系统更严格：回声断言拿文件原始字节与容器里 compose 解析
  后的值比较，`false\r` vs `false` 报"两个一样的值不相等"（Runbook §15.5）。

两条纪律：通过语精确到"证明了什么"；判据按被检查系统的语义归一化，并让失败信息**自证差异**
（同长度直接 `od -c`）。

**2026-09-21 再添两例（#1088 收尾批，判据自身的牙）**：
- **基线即假清零的判据**：`git grep -lE '…' -- 'backend/**/src/main'` 这种 pathspec 写法在
  **基线**上就零输出（目录前缀不带尾部 `/**` 不匹配内容）——"终态为空"因此什么都没证明。
  **行动点：清零判据先在基线上跑一次，确认它有命中（有牙），再在终态跑**；校准式
  `backend/**/src/main/**` 基线命中 4 文件、终态为 0。
- **按错算法写的值检测器**：泄漏扫描的哈希值检测器按 bcrypt 前缀写，而本仓口令哈希是
  **Argon2id**（`$argon2id$…`）——值检查恒空。**行动点：检测器先用阳性对照自证会红**
  （种入真实形状的值）——与 §2"先证明它会红"是同一条纪律，只是对象从测试换成了判据命令。
