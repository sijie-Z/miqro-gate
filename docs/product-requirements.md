# 产品需求

## 1. 背景

客户内部使用多家大语言模型供应商的官方 API、Coding Plan、Token Plan 和团队 Plan。真实 API Key 数量多、更新困难，直接把真实 Key 分发给员工会带来以下问题：

- 真实凭证需要逐个分发和更新。
- 一个团队或项目共用真实 Key 时，无法继续追踪到具体使用者。
- 项目、个人、供应商和模型维度的 Token 与成本难以统一统计。
- 套餐型产品存在周期额度、共享池、席位、成员 Key 等不同计量方式。
- 更换真实 Key 时，需要修改大量本地客户端配置。
- 官方账单与内部使用记录难以对应。

## 2. 产品目标

1. 一个真实上游凭证可映射为多个 Virtual Key。
2. Virtual Key 可以精确归属到用户、项目、供应商产品和用途。
3. 真实凭证轮换时，所有 Virtual Key 与 CC Switch 配置保持不变。
4. 系统统一记录请求、Token、缓存 Token、费用、延迟和状态，支持管理员导出原始流水。
5. 同时支持按量 API、个人 Plan、团队 Plan 和企业 Plan。
6. 普通用户通过门户免审批自助创建、轮换和吊销自己的 Virtual Key。
7. 管理员只需选择预置的供应商产品并录入真实 API Key；其他配置尽量由供应商适配器提供或自动探测。
8. 为 CC Switch 提供稳定的 Base URL、Virtual Key 和 `/v1/models`。

## 3. 非目标

- 不做供应商之间的自动路由、负载均衡或故障切换。
- 不根据价格、速度或质量自动选择模型。
- 不在 Gateway 内做 Anthropic、OpenAI、Gemini 之间的协议转换。
- 不为 CC Switch 生成配置文件，不做一键导入。
- 不保存请求与响应正文。
- 不做硬限流或预算熔断。
- 不自动导入供应商账单，也不自动完成账单对账。
- 不在第一版实现模型响应缓存。
- 不在第一版交付 Kubernetes Helm Chart、OIDC、LDAP 或真正的多租户 SaaS。
- 供应商服务条款、凭证转发授权和套餐使用合规由客户自行负责，不属于系统的产品判断逻辑。

## 4. 用户和权限

### 4.1 系统管理员

系统管理员拥有全部权限：

- 创建、禁用、重置门户账号。
- 管理团队、项目及成员关系。
- 管理供应商产品、真实凭证、个人/团队/企业 Plan。
- 给项目授权供应商产品、真实凭证和模型。
- 查看全局、项目、用户、Virtual Key 和真实凭证维度的统计。
- 查看 Plan 余额、周期剩余、席位和团队共享额度。
- 配置 Webhook 与告警规则。
- 导出或按时间范围删除原始流水。
- 查看永久管理员审计日志。

### 4.2 普通用户

普通用户只能：

- 查看自己参加的项目以及管理员授权的供应商产品和模型。
- 在授权范围内免审批创建 Virtual Key。
- 查看、轮换、吊销自己的 Virtual Key。
- 查看自己的请求数、Token、成本估算和错误情况。

普通用户不能查看真实 API Key、Plan 总余额、项目总量、其他用户数据或管理员审计记录。

## 5. 核心业务规则

### 5.1 Virtual Key 固定映射

一个 Virtual Key 必须固定绑定：

- 一个普通用户；
- 一个项目；
- 一个供应商产品；
- 一个确定的真实上游凭证；
- 一个用途标签，例如 Claude Code、Claude Desktop、Codex 或自定义；
- 一组管理员授权的模型。

Virtual Key 不跨供应商，也不在多个真实凭证间自动选择。切换供应商时，用户应在 CC Switch 中切换到另一个 Virtual Key 对应的 Provider。

### 5.2 自助创建

管理员先完成项目、成员、供应商产品、真实凭证和模型授权。用户在该边界内创建 Virtual Key 不需要审批。Virtual Key 默认永不过期，但可主动轮换或吊销。

### 5.3 真实凭证轮换

管理员录入新真实 Key 后，系统必须先做连通性验证，再原子切换。旧 Key 仅用于等待已经开始的请求结束，随后停用。Virtual Key 和 Base URL 不变化。

### 5.4 明文展示

- Virtual Key 只在创建或轮换成功时显示一次，之后不能找回。
- 真实上游 Key 加密保存，门户永不完整回显。
- 忘记 Virtual Key 后只能轮换。

### 5.5 统计与原始流水

每次推理请求都形成一条不可变用量事件。管理员可以按时间范围导出 CSV 或 JSONL，并在外部与官方账单进行比对。原始流水默认永久保留，直到管理员明确按时间范围手动删除。

## 6. Plan 支持范围

Plan 不是简单的布尔字段。系统至少支持：

- 计费模式：按量、固定订阅、预付 Token、积分池、混合模式。
- 计划范围：个人、团队、企业。
- 凭证拓扑：单共享 Key、多 Key 共享池、每席位独立 Key、每成员 Subscription Key。
- 额度拓扑：整包共享、成员独立、独占额度加共享池、Key 上限、Credits 兜底。
- 周期窗口：滚动小时窗口、自然周、订阅月、自然月、自定义窗口。
- 余额来源：供应商官方 API、本地估算、无法获取。

团队 Plan 必须能够表达团队总额度、成员/席位、多个真实 Key、共享额度池和每 Key 用量。

## 7. 告警

系统不阻断推理请求，但支持管理员配置通用 Webhook。首版必须覆盖：

- 真实凭证验证失败或失效；
- 供应商错误率持续升高；
- 余额或 Plan 剩余低于阈值；
- 用户、项目或 Virtual Key 用量异常增长；
- Gateway、数据库、统计或备份任务异常；
- 供应商响应缺少 usage 数据。

## 8. 容量与性能目标

- 最多 50 个门户账号。
- 支持最多 50 条并发流式请求。
- Gateway 不保存完整请求体，不在热路径调用外部控制服务。
- 客户端断开后，应立即取消上游请求。
- Gateway 自身引入的额外首包延迟 P95 目标不超过 30ms，不包含上游模型耗时。

## 9. 成功标准

- 用户可在 2 分钟内完成登录、创建 Virtual Key 并复制 Base URL 和 Key。
- 管理员轮换真实凭证后，用户无需修改 CC Switch。
- Claude Code、Claude Desktop、Codex 可通过 CC Switch 正常使用已验证的供应商产品。
- 流式文本、工具调用、推理字段、取消和缓存字段不被 Gateway 破坏。
- 每条请求可以追溯到用户、项目、Virtual Key、供应商产品和真实凭证。
- 管理员可导出足以与官方明细进行人工比对的原始流水。
