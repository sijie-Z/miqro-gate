## 1. 需求篇

### 1.1 需求原始语境（技术研讨会，2026-08，逐条保留）

公司内部 AI 编码（Claude Code / Codex / Hermes / WorkBuddy 等）投入持续增长，暴露出四类问题，其中与本文直接相关的两条：

1. **成本不可见**：多个项目、多个部门共用一个上游账号时，无法在 LLM 控制台区分每个项目的真实 token 消耗，**财务无法分摊**；
2. **多项目切换繁琐**：若按项目各发一个 Key，用户在多个项目之间来回切换配置，**体验差、易出错**。

当时的讨论过程（leader 与团队）：

- 提出方案："**一个项目一个映射的虚拟 Key**"——按项目隔离，账单天然可分；
- 随即被自己否掉："**你一个人不是就有几个 Key 了？人不可能在换项目的时候切换（Key），这完全违背人类行为**"；
- leader 提出**后缀**思路：一把 Key 通过后缀区分项目；
- 当时的难点：**不知道怎么实现**——"自动让不同项目用同一个人的虚拟 Key、各自归集，能做出来吗？"
- 团队当时的另一个推测（后被明确否决，见 §4.2）：拦截每一次问答、根据问答和模型回答判断属于哪个项目，再叠加计算。

**结论性需求（本轮落地的目标）**：

> **一个人一把虚拟 Key；这把 Key 能跨多个项目使用；每个项目的用量与费用各自归集。**

### 1.2 需求拆解（可验收条目）

| # | 需求 | 验收点 |
|---|---|---|
| **R1** | 一人一钥 | R1.1 密钥只申请一次；R1.2 轮换只换这一次；R1.3 吊销一条线（吊销/成员移出即时生效） |
| **R2** | 多项目接入 | R2.1 同一把 Key 可用于其有授权的全部项目；R2.2 "切换项目"不换 Key、不复制粘贴；R2.3 对用户尽量零感知 |
| **R3** | 归属确定性 | R3.1 每个请求的归属项目**可确定判定**（不是猜）；R3.2 财务口径可逐条复算、可对账；R3.3 归属声明不可伪造、不可越权 |
| **R4** | 隔离与安全 | R4.1 项目间零串用（授权/凭证/模型范围/用量四个层面）；R4.2 防枚举（探测者无法区分"密钥无效"与"不属于此项目"）；R4.3 防私用靠审计与告警（加密解决不了人的行为） |
| **R5** | 兼容与演化 | R5.1 存量 Key 行为逐字节不变；R5.2 配套机制不制造新地雷（如"改配置废掉存量 Key"） |

### 1.3 与既有产品决策的关系（显式承认）

仓库产品决策原文：*"一个 Virtual Key 固定绑定一个用户、**项目**、供应商产品、真实凭证和用途；不跨供应商，不负载均衡。"*

而《架构设计报告》§3 与《详细设计》V4 表注释（"**一个密钥可绑多个项目**；授权权威关系"）设计的是多绑定——**文档与决策条目自相矛盾，实现当年按 1:1 收缩落地**。本轮经产品负责人（用户）明确指示"一个人一个虚拟 Key 是肯定要实现的"，由 **ADR-0018 修订该条中的"项目"维度**（放开为多项目），其余维度不变：**仍是一把 Key 固定一个用户、一个供应商产品（经绑定 grant）、一个用途；不跨供应商、不负载均衡。**

## 2. 方案篇

### 2.1 一句话方案

**把"项目标签"编进密钥字符串（明文后缀），请求带哪个标签，就在哪个项目上下文里跑——归属靠显式声明（编码解析），不靠任何猜测（自动检测）；授权权威始终在数据库。**

### 2.2 密钥格式与请求路径（核心机制）

**格式**：

```
mqk_live_<publicKeyId>_<secret>[.<projectTag>]
         └─22字符─┘ └─43字符─┘ └─项目标签（明文）─┘
```

- `publicKeyId`/`secret` 为定长 base64url（定长解析，标签可含 `_` 但不可含 `.`）；
- **标签不参与 HMAC 摘要**：改标签既不能提权（HMAC 仍要过），也不会绕过任何授权（授权在库里）；
- 服务端只存摘要；明文密钥只出现于签发时刻与客户端本地配置。

**网关请求路径**（热路径，全内存快照、零数据库）：

```
请求(Authorization: Bearer mqk_live_…_…<.tag>)
  → 解析（定长）                          ┐
  → 按 publicKeyId 查快照 → HMAC 常量时间校验 │ 任一失败：统一 404 VIRTUAL_KEY_INVALID
  → 按 (keyId, 标签) 选择绑定行 ←───────────┘（防枚举：不区分失败原因）
  → 绑定行自带 grant → 解析出 凭证 / 产品
  → 注入该项目真实上游凭证 → 转发
  → 模型门控：Key 模型集 ∩ 该绑定 grant 模型集 ∩ 产品目录 ACTIVE
  → 用量事件携带实际解析出的项目
```

### 2.3 授权模型（两层）

```
Virtual Key（一个人）
   │ 1:N
   ├── key_project_binding（Key × 项目 A）── grant A（项目A的凭证/产品/模型范围）
   ├── key_project_binding（Key × 项目 B）── grant B
   └── key_project_binding（Key × 项目 C）── grant C
```

- **第一层**：Key 对哪些项目有授权（绑定表，逐行审计，可单独禁用）；
- **第二层**：每个绑定走哪个 grant（凭证 + 供应商产品 + 授权模型范围）——**请求解析到哪一行，就用哪一行的第二层**，跨项目天然互不泄漏。

### 2.4 用户工作流：所谓"切换"到底是什么动作

**正解：切换的载体是"你在哪里干活"，不是"改密钥"。**

| 客户端 | 配置方式 | 切换动作 |
|---|---|---|
| CC Switch（Claude Code / Codex / Hermes 等） | 每个项目建一个**条目**：同一个 Key + 各自项目标签 | 切条目（一键/热键）＝切项目 |
| Claude Code（原生） | 项目目录 `.claude/settings.json` 设该项目的 `ANTHROPIC_AUTH_TOKEN`（同 Key + 该项目标签） | **cd 进哪个项目目录，自动就是哪个项目**，无需任何手动动作 |
| WorkBuddy | `models.json` 里配多条（同 Key + 各自标签） | 切模型条目＝切项目 |

"申请一次、吊销一次、审计一条线"：所有条目共享同一把基础密钥。

### 2.5 归属与计量（财务侧）

- 网关在**解析阶段**就确定了请求的项目——**确定性、可复算**，不引入任何概率；
- 用量事件携带实际解析出的项目，既有三口径（上游实付 / 网关观察 / 项目分摊）与对账逻辑完全复用，**计费/对账不需要改任何口径**；
- 项目维度也因此天然支持"一人 × 多项目"的交叉报表（人 → 项目 → 模型）。

### 2.6 为什么是"编码解析"而不是"自动检测"（关键决策）

| | 编码解析（本方案） | 自动检测（内容推断） |
|---|---|---|
| 归属判定 | 请求自带声明，确定性 | 网关读请求内容猜——prompt 常跨项目，不可靠 |
| 隐私 | 不读正文（产品红线：网关不读、不存 prompt/代码/回答） | 必须读正文；若过分类模型还要把正文喂给它 |
| 财务 | 可逐条复算、可入账 | 概率性归属，无法入账 |
| 成本 | 零额外开销 | 每条问答加一次分类调用（成本+延迟） |
| 边界 | 无 | 跨项目问题（"对比 A、B 两个项目"）无解 |

结论：**归属永远靠显式声明，零猜测**——这也是《架构设计报告》§3.2 早已定下的决策（"不做自动检测，做编码解析"）。

### 2.7 实现要点（代码级，均已落地）

| 层 | 改动 |
|---|---|
| 数据库 | **V53 迁移**：`key_project_binding` 增 `grant_id`（回填自 `virtual_keys.grant_id`，存量语义不变）；存量项目标签回填（`proj-<uuid12>`）；表注释修正 |
| 快照/装载 | 去 `DISTINCT ON`，按 `(keyId, 标签)` 复合键装载；每绑定行解析自己的 grant |
| 网关 | `VirtualKeyResolver` 由"后缀等值校验"改为"**按后缀选择绑定**"；`/v1/models` 与推理门控改用绑定 grant |
| 控制面 | 创建接受 `projectIds`（首个为主项目；附加项目按"同产品最早 ACTIVE grant"确定性匹配，缺失 409 中文指引）；轮换**复制全部绑定**；标签自动生成且被引用后不可改（409）；成员移出项目 → 只禁用该项目绑定、无剩余绑定的 Key 置 REVOKED |
| 契约 | `projectIds` 新增（`projectId` 兼容）；`boundProjects` 响应；OpenAPI 基线重导出 |
| 前端 | 建 Key 表单「同时绑定到其他项目（可选）」多选；Key 列表 `+N` 角标（悬停显示全部标签） |

## 3. 对标篇

### 3.1 阿里云（百炼 / DashScope）

- 组织单元是**业务空间（workspace）**；API-KEY 按空间签发，用量与计费**按空间**归集；
- 一个开发者参与多空间 → 需要多把 Key 或切换配置；更细的分摊需要在请求层自行打标（业务侧维护映射）。
- 结论：**归属=空间（显式），一人多空间没有"单 Key 自动归属"的原生能力。**

### 3.2 腾讯云

- 资源隔离靠**主账号/子账号（APPID/UIN）**；
- 成本分摊的标准工具是**费用标签（Tag）**：资源与账单按**显式打上的标签**归集、分账——标签由人/系统显式声明，不是推断出来的；
- 大模型服务的调用凭证同样是"按应用/子账号签发"的模式。
- 结论：同为**显式归属**；细粒度=显式标签。

### 3.3 国际与业界工具

- **OpenAI**：Projects + 每项目独立 API Key，用量按 Project 看板；
- **Anthropic**：Workspaces + 每 workspace 独立 Key，用量按 workspace；
- **LiteLLM（自托管网关，与本产品形态最接近）**：virtual key 可挂 team/user/metadata，**请求级 metadata/tags**做成本归集；多项目=多 key 或按 metadata 打标；
- **Portkey** 等网关：同类——请求头/元数据标签归集。
- 结论：**没有任何产品提供"从对话内容自动判定成本归属"**；行业共识是"key 归属 + 请求级标签"。

### 3.4 共性对照表

| 维度 | 行业通行做法 | 本方案（MiQroKey） |
|---|---|---|
| 归属信息来源 | **显式**：Key 归属空间/项目；细粒度再加请求级标签 | **显式**：项目标签（后缀）编入 Key |
| 一人多项目 | 多把 Key，或同一 Key 在不同工具配置里手工切换 | **一把 Key**，多条目/多目录配置，切换=条目切换 |
| 归属判定 | 查表（Key→空间/项目） | 查表（(Key,标签)→绑定），**零猜测** |
| 细粒度标签 | 请求头/元数据（需要改造客户端或代理） | **免改造**：标签就在密钥字符串里，客户端配置天然携带 |
| 内容推断归属 | 无产品化先例（且各家隐私政策均禁止） | 明确否决（§4.2） |
| 改标签的代价 | 通常=新建 Key/重配 | 标签**被引用后不可改**（409），从机制上消除"改一下废一片" |

### 3.5 我们的差异与创新点（软著叙事）

"**单密钥多项目 + 标签明文路由 + 数据库授权权威 + 轮换不动路由 + 主密钥轮换不影响项目路由 + 标签不可篡改提权**"这一组合，在检索到的行业产品中**没有对应实现**：

- 大厂的"多项目"靠多 Key/多空间——没有回应"人不会切换"这一原始痛点；
- 网关类工具的"请求级标签"要改造请求——我们的标签由客户端配置**天然携带**，用户零改造；
- 我们对"内容推断"的否决与全行业一致，但**"显式声明"与"免改造"的结合**是本方案的独有形态。

这正是《架构设计报告》附录 A 中"基于 HMAC 项目绑定与标签路由的多项目虚拟密钥体系"作为软著创新点的实质内容。

## 4. 难点篇

### 4.1 难点一：一人多项目如何"不切换"？

- 痛点本质：切换成本。老方案（一项目一 Key）的每一步都是成本：记住哪把 Key 对哪个项目 → 复制粘贴 → 配错一个字符 401 → 5 个项目 5 份凭证明细。
- 本方案把成本降到："**切换 = 切换客户端的项目条目 / 走进项目目录**"——这是人已经在做的动作（换项目本来就要换目录/换工具视图），不再有额外的"密钥管理"动作。
- 有人会问：为什么不能连"选择条目"都省掉？因为请求**必须携带归属信息**——这是所有方案的物理下限（要么客户端声明，要么网关猜——后者已否决）。我们做到的是：声明由**配置**完成，用户日常无感。

### 4.2 难点二：能不能让系统按"问答内容"自动判断项目？

**不能。** 四层理由（前三层文档已论证，本轮补充实测视角）：

1. **不可靠**：prompt 经常跨项目（"参考 A 项目的架构给 B 项目写个脚本"）、元问题（"帮我解释下这个报错"）无项目信号——猜错的后果是**记在别人账上**；
2. **隐私红线**：产品承诺"不保存 prompt/代码/回答"，更进一步是"网关不读正文"——为分摊而通读内容、甚至喂给分类模型，等于把红线整体挪走；
3. **财务确定性**：分摊/对账必须**可逐条复算、可被财务信任**；"模型猜的归属"不能入账；
4. **成本与延迟**：每个请求加一次判断调用（或规则），省钱系统反而在烧钱。

行业对照（§3）：没有任何大厂产品这么做。该思路在《架构设计报告》§3.0 已被明确否决（原话："既不可靠又触碰隐私"）。

### 4.3 难点三：改标签会让存量 Key 失效（本轮修复的地雷）⚠️

- 机制：密钥字符串在**签发时刻**冻结了后缀；而实现收缩期网关用"项目**当前**标签"与后缀做等值校验——**给项目改标签/清空标签 = 该项目全部存量 Key 静默 404**（无警告、无计数）。
- 这是文档→实现收缩的次生产物（文档设计里标签是选择器，收缩后变成了等值校验的"校验位"）。
- 本轮修复：**标签被任一绑定引用后不可修改**（409 PROJECT_TAG_IN_USE，含受影响绑定计数与指引）；无引用的标签可自由改；新项目未填标签时**自动生成**（不再要求管理员发明 slug）。两个地雷一并拆除。

### 4.4 难点四：轮换 × 多绑定

- 轮换语义：旧 Key 进入宽限（ROTATING），新 Key 接管；**后缀（标签）不随轮换变化**——与《架构设计报告》§3.4 一致；
- 多绑定后：轮换必须**复制全部绑定行**（本项目已实现）；宽限期内新旧两把 Key 各自按 (keyId,标签) 全量可路由，客户端逐条替换条目即可平滑过渡。

### 4.5 难点五：项目间的隔离（防串用 / 防私用 / 防泄露）

| 威胁 | 机制 |
|---|---|
| 跨项目串用 | 每请求固定解析到**一个**绑定行；凭证注入、模型门控、用量归属全部以该行为准；缓存键本来就含项目维度 |
| 伪造/篡改标签 | 标签不参与 HMAC、不承载权限——篡改只会让 (keyId,标签) 查无绑定 → 统一 404 |
| 枚举探测 | 无效密钥/未绑定标签/他人项目标签 → **全部统一 404**，响应路径一致（模型越权 403 是既有例外：请求方自知所询模型，不构成额外信息泄露） |
| 私用 | 加密解决不了人的行为——靠审计、用量异常检测与告警（既有体系） |
| 泄露 | 服务端只存 HMAC 摘要；明文一次性展示；吊销/成员移出即时生效（快照刷新） |

### 4.6 难点六：存量兼容（零迁移不变量）

- `key_project_binding` 表**从 V4 起唯一约束就是 `(virtual_key_id, project_id)` 对**——结构上一直支持多行，这是"改造量比想象小"的根本原因；
- V53 只做两件"填充"：给每行绑定回填 `grant_id =` 原 `virtual_keys.grant_id`（存量单绑定语义逐字节等价）；给存量空标签的项目回填 `proj-<uuid12>`；
- **不变量声明**：现有全部 Key 的解析结果、可路由标签、模型集、用量归属与迁移前**完全一致**。

### 4.7 难点七（流程教训）：文档与实现的长期一致性

- 本次问题的根因不是"没设计"，而是**设计收缩后没有回写文档**——文档笃定说多绑定，代码笃定做 1:1，两侧长期各自为真；
- 本轮的配套纪律：ADR（决策）+ 本文（完整叙述）+ 契约/库表文档同步 + 集成测试锁行为（多项目创建/轮换镜像/标签守卫/成员移除全有测试），并修正了另一处同类"文档承诺但从未实现"（成员移出项目 → Key 失效）。

## 7. 术语表

| 术语 | 含义 |
|---|---|
| 虚拟 Key | 网关签发的密钥，明文仅展示一次，服务端存 HMAC 摘要；格式 `mqk_live_<id>_<secret>[.<tag>]` |
| 项目标签（projectTag） | 密钥后缀中的项目标识（明文、不参与 HMAC、不承载权限）；被绑定引用后不可修改 |
| 绑定（key_project_binding） | Key × 项目 的授权行，自带 `grant_id`；"哪个标签命中哪一行"即归属判定 |
| Grant（项目授权） | 项目 × 供应商产品 × 凭证 的授权（含模型范围）；由绑定行引用 |
| 路由快照 | 网关内存中的版本化只读表；热路径零数据库；变更经 NOTIFY 秒级生效 |
| CC Switch | 本地客户端配置管理器；每项目一条目（同 Key + 各自标签），切条目=切项目 |
| 编码解析 / 自动检测 | 两种归属路线：前者=请求显式携带标签（本方案）；后者=读内容猜（已否决） |
| 四层隔离 | 授权（绑定）× 凭证（grant）× 模型范围（grant 模型集）× 用量（事件携带项目） |
