## 0. 先读这一节：三个必须先纠正的命名事实

接手时最容易踩的坑——题面/口头传说里的表名与代码里的实际表名不一致：

| 你听到的名字 | 数据库里真实的名字 | 证据 |
|---|---|---|
| `usage_events` | **`usage_event`（单数）** | `V6__usage_events.sql:17`（文件名是复数，表名不是） |
| `price` / `prices` | **`price_snapshot`** | `V5__cache_and_price_tables.sql:52`；全仓无 `CREATE TABLE prices` |
| `credential` | **`upstream_credentials` + `upstream_credential_versions`** | `V1__core_tables.sql:281,316` |
| `quota` | **`quota_rules`（计划）/ `quota_snapshots`（状态）/ `quota_enforcement`（判定集）** | V23 / V9 / V59 |
| `key_project_bindings`（复数） | **`key_project_binding`（单数）** | `V4__virtual_key_tag_routing.sql` |
| `PriceBasis` 枚举 | **`RowPriceBasis`（record，不是 enum）** | `backend/domain/src/main/java/com/miqroera/miqrokey/domain/usage/RowPriceBasis.java:35` |
| `retention_log` in schema doc | 文档 `docs/database-schema.md` **完全没有收录该表**（grep 命中 0） | 见 §11 |

另外：**全库从未 DROP 或 RENAME 过任何表/列**。所有 `DROP` 只出现在放宽 CHECK 约束时（`alert_rules_type_check` 六次、V58 的 quota 枚举）。共 68 张表全部存活。

## 1. 控制面分层

### 1.1 模块依赖（谁依赖谁）

```
domain            ← 纯领域：模型 + 仓储接口 + 服务接口（仅依赖 re2j，无 Spring）
persistence-postgres ← 仓储实现 + Flyway 迁移 + AuditServiceImpl（依赖 domain）
control-plane-app    ← Controller + Service + Security + 调度（依赖 domain + persistence-postgres）
gateway-app          ← 数据面（只 `<scope>test</scope>` 依赖 control-plane-app，见 gateway-app/pom.xml:80-84）
```

关键点：`domain` 只放**接口**（`domain/repository/*.java` 41 个、`domain/service/*.java`）、`persistence-postgres` 放**实现**（`persistence/repository/*Impl.java` 43 个）。控制面 Service 注入的是 `domain.repository.*` 接口，实现由 Spring 在持久化模块中提供——**换存储只改 persistence-postgres**。

### 1.2 三层职责

| 层 | 位置 | 数量 | 职责 |
|---|---|---|---|
| Controller | `backend/control-plane-app/src/main/java/com/miqroera/miqrokey/controlplane/controller/` | 60 个文件 | 路由、Bean Validation、审计落点、调用 Service。**几乎不含业务规则** |
| Service | `.../controlplane/service/` | 74 个文件 | 业务规则、事务边界（`@Transactional`）、审计调用、跨仓储编排 |
| Repository 接口 | `backend/domain/.../domain/repository/` | 41 个 | 存储契约 |
| Repository 实现 | `backend/persistence-postgres/.../persistence/repository/` | 43 个 | `NamedParameterJdbcTemplate` 手写 SQL（**不用 JPA**） |
| 领域模型 | `backend/domain/.../domain/model/` | 80+ 个 record | 不可变 record，compact 构造器做校验（如 `QuotaRule.java:20-38`） |

**唯一的跨层特例**：`persistence-postgres/.../persistence/service/AuditServiceImpl.java` 是**领域服务接口 `domain.service.AuditService` 的实现**，但因为它要持有 `pg_advisory_xact_lock` 与链头读取，被放在持久化模块而非控制面。这是"审计链必须在一次事务内完成 read→insert"的直接后果。

**Controller 直连 JDBC 的例外**：`QuotaEnforcementService`（Service 层）直接用 `NamedParameterJdbcTemplate` 读写 `quota_enforcement`，因为它操作的是**派生判定集**而非聚合根，没有对应仓储接口。接手时不要以为所有 SQL 都在 persistence 模块。

> 🔴 **V70 是这一批里唯一能把控制面卡死的迁移，升级前必读**（#1249，**仍 OPEN**）
>
> `V70` 用**非幂等**的 `CREATE UNIQUE INDEX uq_usage_adjustments_reversal_of`（不是 `IF NOT EXISTS`，也和同批 `V69` 明写 *Idempotent on purpose* 的做法相反）。有**两条 100% 必现**的路径让它失败：
>
> - **路径 A**：库里已存在"一笔原始调整的两条冲销行"。**这不是人为构造的状态**——#999 之前 `UsageAdjustmentService.reversalOf()` 没有任何"已被冲销"检查，所以 **V63–V69 期间可以通过公开 API 产生**重复冲销行。
> - **路径 B**：运维照 `V69` 注释里的建议**带外**跑过 `CREATE UNIQUE INDEX CONCURRENTLY`，同名索引已存在。
>
> **真正要命的是失败之后的形状**：PostgreSQL 的事务性 DDL 把「迁移执行 + 迁移表插入」**一起回滚**，所以 `flyway_schema_history` 里**连一行 `success=false` 都不留**。于是：
>
> 1. `flyway repair` 报 *"No failed migration detected"* —— **空转，修不了**；
> 2. 控制面**此后每次启动都停在同一个地方**，没有自动恢复路径；
> 3. 出路只有人工：按下面的语句查重、由 owner 决策怎么处理那些行，或人工 `DROP INDEX`。
>
> ```sql
> SELECT tenant_id, reversal_of_id, count(*) FROM usage_adjustments
> WHERE reversal_of_id IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1;
> ```
>
> ⚠️ 这段前置查重**只写在 V70 的 `.sql` 注释里**——全仓 grep `uq_usage_adjustments_reversal_of` 除 V70 本身外零命中，**发布检查单和运维手册里都没有**。即"发布前由业主决策"这条要求**目前没有可执行入口**。
> **接手后值得优先做的一件事**：把这段查重做成 `deploy/` 下的可执行脚本并挂进发布检查单。

### 4.4 冻结价格基座（F21-A）—— `base_cost_amount` 与"未定价"

**问题**（`V64` 文件头 :4-8）：原成本是查询时用 `token × 查询时刻最新价目` 现算，**改一次价目，所有历史报表金额跟着变**。

**方案**：不引外键，而是把**四个单价 + 元数据直接盖章到 `usage_event` 行上**（V64），再额外盖一个事件级 `base_cost_amount`（V66）。

`usage_event` 的价格冻结列（`V64__usage_event_price_snapshot.sql:35-43`）：

| 列 | 类型 | 语义 |
|---|---|---|
| `price_input` / `price_output` / `price_cache_read` / `price_cache_creation` | numeric(24,10) | 事件采用的四维单价（与 `price_snapshot.unit_price` 同量纲） |
| `price_currency` | varchar(3) | 币种 |
| `price_effective_from` | timestamptz | **所采用价格行的生效时刻（不是事件时刻）** |
| `price_source` | varchar(32) | `MANUAL`/`OFFICIAL`/`ESTIMATED` |
| `price_status` | varchar(16) | `COMPLETE`/`PARTIAL`/`UNAVAILABLE`；**列 NULL = 尚未评估** |

**`base_cost_amount` 是什么**：该事件**在事件发生时点、依据当时价目**算出的基础成本，与 `price_currency` 成对解读。唯一算法 `UsagePriceBackfillService.baseCost(...)`（`.../service/UsagePriceBackfillService.java:507-520`）：只累加"既有 token 又有冻结单价"的维度；一个维度都没价 → 返回 **null（不是 0）**；除法走 `UsageStatsAggregator.dividePerMillion`。

**"未定价"的三层表示（全部禁止用 0 冒充）**：

| 层 | 表示 | 位置 |
|---|---|---|
| 存储 | 单价列与 `base_cost_amount` 为 **NULL**；`price_status` 独立列：**列 NULL = 尚未评估**，另有 `COMPLETE`/`PARTIAL`/`UNAVAILABLE` | `V64:19-22,45-47,58-61`；`V66:11-18` |
| 回填判定 | Java `classify(row)` 返回三态字符串：参与维度全有价→COMPLETE；部分→PARTIAL；一个都没→UNAVAILABLE | `UsagePriceBackfillService.java:471-488` |
| 读/聚合 | SQL 侧 `zeroIfUnpriced(price) = COALESCE(price, 0)`（对已知金额贡献 0）+ `unpricedColumns` 单独统计缺口 | `UsageStatsRepositoryImpl.java:271-273,291-315` |
| 单行 | `RowPriceBasis` 分量为 null = 该维度无价；`UsageRecordView.priced=false` | `RowPriceBasis.java:20-23,38`；`UsageRecordPage.java:36-37,45-46` |

**V66 的核心语义约束**（`V66__usage_event_base_cost.sql:11-18`）：
- `price_status = COMPLETE` → `base_cost_amount` 有值（**可以是 0**，表示确实免费）
- `price_status = PARTIAL` → 只含已定价维度的部分和
- `price_status = UNAVAILABLE` → `base_cost_amount` 为 **NULL（不是 0）**

**"补价"必须走追加式**（V66 文件头 :21-24）：用 #709 的 COST 维度调整，**不修改本列、也不把 `price_status` 从 UNAVAILABLE 改成 COMPLETE**——"事件发生时没有价格"是一个不该被抹掉的事实。

**回填路径三趟**（入口 `POST /api/v1/admin/usage-price-backfill`，`AdminUsagePriceBackfillController.java:33,54-60` → `UsagePriceBackfillService.backfill(...)` :282-325）：

```sql
LEFT JOIN LATERAL (
    SELECT COALESCE(SUM(a.input_tokens_delta), 0) AS input_delta,
           COALESCE(SUM(a.output_tokens_delta), 0) AS output_delta,
           COALESCE(SUM(a.cache_read_tokens_delta), 0) AS cache_read_delta,

```

净额表达式（:98-101，**NULL 保留语义**：既无观测又无 delta 时保持 NULL，不读成 0）：
```java
netExpr(observed, delta) =
  "CAST(CASE WHEN " + observed + " IS NULL AND COALESCE(" + delta + ", 0) = 0 THEN NULL
             ELSE COALESCE(" + observed + ", 0) + COALESCE(" + delta + ", 0) END AS bigint)"
```

```sql
(COALESCE(adj.adjustment_count, 0) > 0)
```

## 5. 配额

### 5.1 数据模型

配额分四张表各司其职：

| 表 | 角色 | 关键点 |
|---|---|---|
| `quota_rules`（V23/V58/V59） | **计划**：limit of (metric × period) per scope | 唯一 `(tenant, scope_type, scope_id, metric, period)`；**水位不入库**，读时从 usage_event 现算 |
| `quota_snapshots`（V9） | **上游官方配额状态**（订阅/席位/凭证三级） | `source ∈ OFFICIAL_API / LOCAL_ESTIMATE / UNAVAILABLE`——**产品没有官方余额 API 时写 UNAVAILABLE，绝不编造** |
| `quota_default_template`（V26/V58） | 新用户建卡时自动复制的规则模板 | 每租户一行 |
| `quota_enforcement`（V59） | **判定集**（派生、可重建） | 一行/超限的 ACTIVE REJECT 规则 |

领域枚举：`QuotaMetric`（TOKENS/REQUESTS/COST）、`QuotaPeriod`（DAILY/WEEKLY/MONTHLY/YEARLY，**UTC 日历切片**，周从周一起）、`QuotaScopeType`（USER/PROJECT）、`QuotaAction`（`ALERT`/`REJECT`）、`QuotaRuleStatus`。`QuotaRule` record 的 compact 构造器（`domain/model/QuotaRule.java:20-38`）强制 `limitValue > 0`、`warnPercent ∈ 1..99`、`action == null → ALERT`（兼容存量行与旧客户端）。

### 5.2 软着陆（ADR-0020）在代码里的实现

**关键设计**：**判定在控制面，执行在数据面；网关热路径零查询、零计数、零算术**（ADR-0020 §D4）。

```
QuotaEnforcementService（@Scheduled 60s）
  → 遍历 ACTIVE REJECT 规则，经 QuotaWatermarks 算当期水位（与配额页同一份计算）
  → 超限者整体替换写入 quota_enforcement
  → 判定集变化时才 RouteRefreshPublisher.publishChanged()
  → 网关快照携带 quotaBlockedUsers / quotaBlockedProjects（作用域 → 最早窗口结束）
  → 准入处查内存 Map → 429 + Retry-After
```

**① 水位计算** `QuotaWatermarks.evaluate(tenantId, rule)`（`.../service/QuotaWatermarks.java:34-55`）：
- 窗口由 `AdminQuotaRuleService.window(period)`（**`:195`**）按 UTC 日历算；**用 `usageStatsService.summaryObservedUncapped(...)`**（`AdminUsageStatsService.java:163`，调用点 `QuotaWatermarks.java:52`；名字里的 "observed-only" 限定，`#1002`）绕过公开用量 API 的 93 天窗口上限（YEARLY 会超）
- 指标映射：`TOKENS → totals().tokens().total()`、`REQUESTS → totals().requests().upstream()`（**缓存命中不计，不消耗上游配额**）、`COST → totals().cost().upstreamPaid()`
- 四档：`usedPct >= 100 → EXCEEDED`；`>= 90 → NEAR_LIMIT`（固定 90%，Tencent 对齐，常量 `NEAR_LIMIT_PERCENT = 90` :24）；`>= warnPercent → WARNING`；否则 `NORMAL`（:49-53）
- **配额只读 observed，不纳入 usage_adjustments**（V63 分层语义第 4 条）

**② 判定集刷新** `QuotaEnforcementService.evaluate()`（`.../service/QuotaEnforcementService.java:50-87`）：
- `@Scheduled(fixedDelayString = "${miqrokey.quota.enforcement-interval-ms:60000}", initialDelayString = "${miqrokey.quota.enforcement-initial-delay-ms:45000}")` + `@Transactional`
- 取 `findAllActiveReject()`（:53），逐条算水位；
- **单规则异常隔离**（:61-64）：一条规则算错**保留其上一轮判定**，而不是清空整个判定集
- **整体替换**：比对 `before`/`after` 集合（:67-71），**相同则零写入零广播**（early return :69-71）；否则 `DELETE FROM quota_enforcement` + 逐条 `INSERT`（:72-83）+ `routeRefreshPublisher.publishChanged()`（:84）

`quota_enforcement` 表结构（`V59__quota_soft_enforcement.sql`）：`rule_id` PK、`tenant_id`(FK CASCADE)、`scope_type`、`scope_id`、`metric`、`period`、**`window_end timestamptz`**、`blocked_at`。`window_end` 是**评估时刻该规则窗口的结束时间**——它喂给 429 的 Retry-After。

**③ 快照装载** `JdbcRouteSnapshotLoader.loadQuotaEnforcement()`（`backend/route-snapshot/.../JdbcRouteSnapshotLoader.java:98-108`）：
```sql
SELECT scope_type, scope_id, window_end FROM quota_enforcement
```
按 scope 用 `merge(scopeId, until, (a,b) -> a.isBefore(b) ? a : b)` **取最早窗口结束**（:103）——同一作用域被多条规则拦截时，取最早能自愈的时刻。

**④ 网关准入** `QuotaGate.requireNotExceeded(AuthContext)`（`backend/gateway-app/.../vkey/QuotaGate.java:20-29`）：
- 先查 user（:21-24），再查 project（:25-28）——**判定按 scope 而非按 Key**，同一用户/项目下其余 Key 一并生效
- 抛出 `AuthFailureException(HttpStatus.TOO_MANY_REQUESTS, "quota_exceeded", ..., retryAfterSeconds)`（:31-36）
- `retryAfterSeconds(until) = max(1, Duration.between(now, until).getSeconds())`（:43-45）——**不低于 1 秒**
- Header 落地：`ProxyController.java:872-873` 与 `ModelsController.java:118-119` 设 `Retry-After`

**边界**（ADR-0020 §D5/D6，代码注释同样声明）：判定集默认 60s 刷新一轮，**不包含评估间隔内新产生的用量**；"卡在恰好 100%"不可承诺；页面与网关可能在一个周期内不一致。不做限流、不做预算硬熔断、MCP 面不在首版。

### 5.3 配额刷新的事务处理（两阶段）

在 `QuotaSnapshotService`（`.../service/QuotaSnapshotService.java`），**问题背景 #728**：上游 provider 的余额查询是阻塞 HTTP，原来的 `@Transactional` 方法会**占着连接池连接最长 N×20s**，而且定时任务自调用会静默跳过事务注解。

**两阶段实现** `refresh(tenantId, subscriptionId)`（:165-194）：
- **阶段一（无事务）**：逐凭证调 `fetch(adapter, ...)` 收集快照行 → 放进 `List<QuotaSnapshot> rows`（:181-192）。注释明确："provider fetches are blocking HTTP calls and deliberately run *outside* any database transaction"（:156-160）
- **阶段二（短写事务）**：`transactionTemplate.executeWithoutResult(status -> rows.forEach(snapshotRepository::insert))`（**:193**）——收集完成后的行**一次性写入**，`TransactionTemplate` 是构造器里手工 new 的（:109），避免自调用失效
- 两条入口共用此路径：admin 手动触发与 `@Scheduled` 定时（:133-142）走同一方法，杜绝"定时路径没事务"的坑

`QuotaSnapshotService` 同时负责：`UNAVAILABLE` 诚实表达（无 ACTIVE 凭证或无适配器时，:187-189）、`LOCAL_ESTIMATE` 行（有 `quota_total` + `period_start` 时，:190-192）、密码只在调用内解密并清零（类注释 :69-73）。

2. **summary 归一化**：`repository.normalizeChangeSummary(changeSummary)`（:106）→ `AdminAuditEventRepositoryImpl.java:56-65`，SQL 是 `SELECT (:value)::jsonb::text` —— **借 PostgreSQL 自己的 jsonb 解析器往返一次**，返回的文本就是 `change_summary::jsonb` 列将来会存的形态
3. **取链锁**：`repository.acquireChainLock()`（:111）→ `AdminAuditEventRepositoryImpl.java:69-72`：`SELECT pg_advisory_xact_lock(?)`，固定 key `CHAIN_LOCK_KEY = 1234567890123456789L`（:53），**事务级、提交即释放**
4. **读前任 + 算哈希 + 插入**：`findMostRecent()`（:116）→ `computeEventHash(...)`（:125-126）→ `repository.insert(event)`（:132）→ `Arrays.fill(previousHash, 0)` 清零（:136）

**链头选择**：`findMostRecent()` 用 `ORDER BY chain_position DESC LIMIT 1`（`AdminAuditEventRepositoryImpl.java:47`）——**DB 单调序列，不用 `created_at`/`id`**。理由（类注释 :40-47）：JVM 时钟与随机 UUID 在并发写者下会因果失序，锁前的 `Instant` 可能与提交顺序矛盾，会让链分叉。

**哈希编码** `computeEventHash(...)`（:147-188）是 `public static`，便于校验工具复用。canonical 编码顺序（注释 :139-145）：
```
previousHash(32B) || id(16B MSB) || tenantId(16B) || actorId(16B, 或全零)
  || len+action(UTF-8) || len+targetType(UTF-8) || targetId(16B, 或全零)
  || len+changeSummary(UTF-8) || len+adminRequestId(UTF-8) || createdAt(epoch millis, 8B BE)
```
→ SHA-256。创世哈希 = 32 字节全零（`GENESIS_HASH` :69）。**每个字段都带长度前缀**，避免拼接歧义。`createdAt` 取 `toEpochMilli()` 而非微秒——微秒只用于保证**落库时间戳**可复现，哈希用毫秒。

### 6.3 微秒时间戳截断

**方法**：`AuditServiceImpl.record`，**`AuditServiceImpl.java:98`**：
```java
Instant now = Instant.now(clock).truncatedTo(java.time.temporal.ChronoUnit.MICROS);
```

原因（注释 :91-97，issue #362）：Windows 类时钟暴露 100ns 刻度，而 pgjdbc 会把亚微秒位**四舍五入**进 PG 的微秒 `timestamptz`——锁前值如 `<sec>.9999996s` 被存成下一秒毫秒，而哈希覆盖的是原值，**约 1/2000 的事件在高负载下哈希重算失败**。微秒对齐的 instant 会被精确保存，落库时间戳逐位可复现。回归测试：`control-plane-app/src/test/.../AuditChainIntegrityTest.java:590-610`（断言 `createdAt().getNano() % 1000 == 0`）。

### 8.1 canonical 格式

定义：`ReconciliationTypes.BillLine`（`.../service/reconciliation/ReconciliationTypes.java:16-19`）：

上传的是 **JSONL**，每行一个 JSON object；**JSON key 是 snake_case**（`provider_request_id`、`occurred_at`、`model_id`、`provider_product_code`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`amount`、`currency`、`status`、`provider_row_ref`）——见 `CanonicalBillParser.toBillLine`（:62-72）。

> ⚠️ **各供应商私有格式 → canonical 的解析器未实现**（类注释 :13-19 标注 WAITING_FOR_SAMPLE）。当前只接受已符合 canonical 的 JSONL。

### 8.2 匹配级别（**代码是 3 级锚点 + 1 级桶聚合，不是文档写的"四级"**）

### 9.2 `RoleInterceptor` 怎么工作

`.../security/RoleInterceptor.java`，注册于 `config/SecurityConfig.java:121`（`addPathPatterns("/api/**")`，在 `OriginInterceptor`、`CsrfInterceptor` 之后）。`preHandle` 逻辑（:31-96）：

2. **deny-by-default**（:38-47）：`path.startsWith("/api/v1/admin/")` 时，未认证 → 401；`role != SYSTEM_ADMIN` → 403（中文提示"该操作需要系统管理员（SYSTEM_ADMIN）权限。"）
3. 否则读 `@RequireRole`（方法级优先于类级，:57-65），无注解则放行（:67-69）
4. SYSTEM_ADMIN 对任意 `@RequireRole` 都放行（admin override，:79-81）；非管理员走**精确角色相等**（:83-87）

错误响应是手写 JSON（`application/problem+json`），**显式设 UTF-8**（:105-107 注释 #630：否则 servlet writer 默认 ISO-8859-1，中文标题变 `?`）。

> ⚠️ **`@RequireRole` 注解全仓 0 处使用**（`grep -rn '@RequireRole' backend/ --include=*.java` = 0）。它只被 `RoleInterceptor` 引用（定义 + 拦截器两个文件）。**实际生效的只有第 2 步的路径前缀 deny-by-default**。接手时不要以为在 controller 上加了 `@RequireRole` 就会生效——它会生效，但当前无人使用；也不要以为去掉它会削弱保护。

**路径归一化的安全意义**（`RequestPaths.java` 类注释，issue #723）：Spring MVC 按 *lookup path* 路由（**去除 `;...` 分号参数、解码百分号编码**）。若安全判断用 `getRequestURI()`，则 `/api/v1/admin;x/users` 能到达 admin handler 而 `startsWith("/api/v1/admin/")` 返回 false——**deny-by-default 被绕过**（2026-09-17 线上证实）。`RequestPaths` 在框架 helper 之上再做两次处理：对**解码后**的路径去分号（框架是先剥分号再解码，`%3B` 能存活），并折叠重复斜杠。

### 9.3 认证链与各面的保护方式

**Servlet Filter 链**（`config/SecurityConfig.java` + `config/OpenAdminApiSecurityConfig.java`）：

| 顺序 | Filter | URL 模式 | 作用 |
|---|---|---|---|
| -110 | `AdminIpAllowlistFilter` | `/api/*` | 管理门户 IP 白名单（F05），空名单 = 全放行 |
| -100 | `SessionFilter` | `/api/*` | 会话校验；**放行** `/api/v1/billing/*` 与 `/api/v1/admin-api/*`（各有自己的 filter） |
| -95 | `AdminApiKeyAuthFilter` | `/api/v1/admin-api/*` | 机器密钥或 SYSTEM_ADMIN 会话 |
| -90 | `ApiKeyAuthFilter` | `/api/v1/billing/*` | 消费者密钥或 SYSTEM_ADMIN 会话 |

`SessionFilter` 的公开路径白名单（`SessionFilter.java:51-53`）：`/api/v1/auth/{login,bootstrap,register,registration-status}`、`/api/v1/auth/oauth/{providers,start,callback}`。此外每个请求校验：用户状态（DISABLED 拒绝、LOCKED 未到期拒绝且撤会话）、空闲超时、绝对过期、**强制改密闸**（`mustChangePassword` 时只放行 password/logout/me/csrf）。

**各面的实际保护**：

| 路径 | 保护 |
|---|---|
| `/api/v1/admin/**` | RoleInterceptor deny-by-default → SYSTEM_ADMIN |
| `/api/v1/admin-api/**` | AdminApiKeyAuthFilter（机器密钥 `mqk_admin_…` 或 SYSTEM_ADMIN 会话）+ 能力组 scope |
| `/api/v1/billing/**` | ApiKeyAuthFilter（消费者密钥 `mqk_api_…` 或 SYSTEM_ADMIN 会话）+ 消费者能力组 |
| `/api/v1/me/**`、`/api/v1/skills` | **仅"已登录"**——靠 Controller 从 `userContext.getUser()` 取身份做自限定（`MeVirtualKeyController.java:46-53`、`SkillController.java:35-46`）。**没有额外的角色检查** |

**CSRF**（`security/CsrfInterceptor.java:41-80`）：只对 `/api/**` 的**变更方法**生效；公开端点豁免；**开放管理面的机器密钥调用豁免**（:59-64，机器通道无 cookie，bearer digest 已经认证过）；SYSTEM_ADMIN **浏览器会话仍然要过 token 检查**。令牌读 `X-CSRF-Token` 头，比对会话的 `csrfDigest`。

**资源归属**（`security/OwnershipService.java:50-61`）：`assertSelfOrAdmin(resourceOwnerId, currentUser)` —— 非本人且非 SYSTEM_ADMIN 时抛 `ResourceOwnershipException`，**映射为 404 而非 403**（资源隐藏，防 IDOR 枚举）。

### 9.4 scope 能力组

**两套并行的能力组**，语义分离、不混用：

**① 管理机器密钥**（`domain/model/AdminApiKeyCapabilities.java`，ADR-0015 批 3），4 个码：
```java
USAGE_READ      = "usage:read"
ALERTS_WRITE    = "alerts:write"
EXPORTS_CREATE  = "exports:create"
VKEYS_DELEGATE  = "vkeys:delegate"
```
- 存储：`admin_api_keys.scope jsonb`（V35）。**NULL = 全量**；空数组 = 全拒
- 校验：`isValid(List<String>)`（:29-40）拒绝 null 元素、未知码、重复码 → 400 `ADMIN_API_KEY_SCOPE_INVALID`
- **强制点**：`AdminApiKeyAuthFilter.scopeAllows`（:120-127）+ `capabilityFor(path)`（**:130-146**）的「路径→能力组」映射：
  - `/usage/`、`/audit-events`、`/api-keys`、`/quota-rules`、`/mcp-access-logs` → `usage:read`
  - `/alert-rules`、`/webhooks` → `alerts:write`
  - `/export-tasks` → `exports:create`
  - `/virtual-keys` → `vkeys:delegate`
  - 其他 → `null`（`scopeAllows` 返回 false → 拒绝）
- 拒绝时：记审计 `ADMIN_API_KEY_SCOPE_DENIED`（有发行管理员时，:148-157）+ 403 `ADMIN_API_SCOPE_DENIED`
- **SYSTEM_ADMIN 会话不受 scope 限制**（filter 第 72-83 行的会话短路分支根本不查 scope）

**② 外部消费者**（`domain/model/ConsumerCapabilities.java`，issue #316），2 个码：
```java
BILLING_READ = "billing:read"   // 控制面 /api/v1/billing/**
MCP_CALL     = "mcp:call"       // MCP 数据面
```
存储 `api_consumers.capabilities jsonb`（V37），同样 NULL = 全权。强制在 `ApiKeyAuthFilter` 与 MCP 数据面各自 fail-closed。

## 10. 开放管理 API（ADR-0015 / ADR-0016）

### 10.1 机器密钥 `mqk_admin_` 的认证链路

**发行**（`AdminApiKeyService.issue`，`.../service/AdminApiKeyService.java:42-59`）：
- `AdminApiKey.generateKey()`（`domain/model/AdminApiKey.java:47-53`）：20 字节随机 → hex → `prefix = "mqk_admin_" + hex[0..8)`，`plaintext = prefix + hex[8..]`；**存 SHA-256 digest，明文只返回一次**
- 前缀常量 `PREFIX = "mqk_admin_"`（:28），与外部消费者前缀 `mqk_api_` **显式区分**（:27 注释）
- 拒绝已过期的 `expiresAt`（:45-47，400 `API_KEY_EXPIRES_INVALID`）；同名冲突 409 `ADMIN_API_KEY_NAME_TAKEN`
- 审计 `ADMIN_API_KEY_ISSUE`

**认证**（`AdminApiKeyAuthFilter.doFilterInternal`，`.../security/AdminApiKeyAuthFilter.java:65-98`）：
1. 路径不以 `/api/v1/admin-api` 开头 → 直接放行（:68-71）
2. **若已有门户会话**：要求 SYSTEM_ADMIN，否则 403 `ADMIN_API_FORBIDDEN`；通过后设 `TENANT_ATTR` + `ISSUER_ATTR` = 会话用户（:72-83）
3. 否则读 `Authorization: Bearer mqk_admin_…`（:84-87）：
   - `authenticate(token, request)`（:100-113）：`repository.findActiveByDigest(sha256(token))`；**每请求直读库**（吊销即时生效）；写入四个 request attribute：`KEY_ATTR`、`TENANT_ATTR`、`NAME_ATTR`、`ISSUER_ATTR`（= `key.createdBy()`）、`adminApiKeyCapabilities`
4. **能力组 scope 校验**（:88-92，见 §9.4）
5. 全部失败 → 401 `ADMIN_API_KEY_INVALID`

`ISSUER_ATTR` 的语义（:43-48）：**机器密钥的委托执行者 = 发行该密钥的管理员**；SYSTEM_ADMIN 会话则是会话用户。

**注册**：`config/OpenAdminApiSecurityConfig.java:22-30`，`addUrlPatterns("/api/v1/admin-api/*")`，order `-95`（在 SessionFilter 之后）。

### 10.2 写面的"执行者语义"（ADR-0016）

核心矛盾（ADR-0016 背景段）：机器身份 = 租户级系统主体，**没有 userId**；而 schema 里 `created_by` 类列都指向 `users` 行。

**采 A+C 组合**：

**C —— 无执行者列的配置写直接开**：`/api/v1/admin-api/alert-rules`、`/api/v1/admin-api/webhooks` 全生命周期（表无 `created_by`，tenant 参数即隔离边界）。

**A —— 有执行者列的操作用委托**：`created_by` = 密钥的**发行管理员**。实现方式统一为 Controller 里的一个私有方法：

```java
private static UUID issuerId(HttpServletRequest request, UUID tenantId) {
    UUID issuer = (UUID) request.getAttribute(AdminApiKeyAuthFilter.ISSUER_ATTR);
    if (issuer == null) {
        throw new ApiException(HttpStatus.FORBIDDEN, "EXECUTOR_UNKNOWN", "无法确定执行委托人：该机器密钥缺少发行管理员。");
    }
    return issuer;
}
```
（`OpenAdminExportsReadController.java:72-78`、`OpenAdminVirtualKeysController.java:84-90`）

**Virtual Key 委托创建**（ADR-0016 批 2 v2，案 1）：`POST /api/v1/admin-api/virtual-keys`，body = `CreateVirtualKeyRequest` 字段 + `userId`。委托语义在 `VirtualKeyService.createForUser(...)`（`.../service/VirtualKeyService.java:121-136`）：
- **operator 现行角色必须仍是 SYSTEM_ADMIN**，否则 403 `DELEGATION_FORBIDDEN`（:126-129）——**防止被降权的历史委托人继续借钥扩散凭据**
- 目标用户须租户内存在（404 `TARGET_USER_NOT_FOUND`，:130-131）且 ACTIVE（409 `TARGET_USER_INACTIVE`，:132-134）
- 关键边界（:135）：`createKey(tenantId, target, target.id(), request, requestId, operator.id(), target.id())` —— **成员/授权/模型/cachePolicy 校验按 `target` 执行**（第 2 参 memberSubject = target），归属 `ownerUserId` = 目标，`actorId` = operator，`delegatedTargetId` = 目标
- 与自助建钥完全同一套不变量（1:1 绑定、secret 一次性）
- 审计双元：action `VIRTUAL_KEY_CREATE`，**actor = 委托人**（机器永不冒充用户），`change_summary` 带 `targetUserId`——可同时回到"谁执行"与"钥归谁"

**导出创建委托**：`ExportTaskService.create(tenantId, issuer, format, from, to)`，`created_by` = 发行管理员，审计沿机器密钥。

> **未开放**（ADR-0016 明确排除）：配额/模板写、审批流等依赖"本人"语义的端点。
