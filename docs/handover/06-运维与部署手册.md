## 〇、运维前必读的三件事

### 1. 本系统**默认不限流、不做预算熔断**（但 REJECT 规则会自产 429）

- **429 有两类来源，必须先分清是哪一类**（ADR-0020 落地后网关会自产 429）：
  - **上游供应商限流** —— 供应商返回的
  - **本系统配额超限** —— 标记为 `REJECT` 的配额规则超限时，网关自产 `429` + 标准错误信封（`type=quota_exceeded`，文案含恢复路径）+ **`Retry-After`**（秒，指向该作用域的重置时间）
  - ⚠️ **不要再按「429 只可能来自上游」归因**——该表述在 ADR-0020 落地后已过时（`docs/operations-runbook.md` §14.3 已订正；代码见 `QuotaGate.java`）
- **403 全部来自本系统授权层**
- 想让配额阻断请求，必须在配额规则上显式标记 `REJECT`

### 2. 三类凭据**端点各认各的，混用一律 401**

| 凭据 | 前缀 | 认哪些面 |
|---|---|---|
| Virtual Key | `mqk_live_` | **只认推理面**（`/v1/**`） |
| 消费者 API Key | `mqk_api_` | **只认计费/MCP 面**（`/api/v1/billing/**`、MCP 数据面） |
| 管理机器密钥 | `mqk_admin_` | **只认开放管理 API**（`/api/v1/admin-api/**`） |
| 消费者 JWT | 三段式 | 按各面要求 |

> 这是运维最常踩的坑，详见 `docs/operations-runbook.md` §14.1。

### 3. 供应商账单 **T+1 才稳定**

对账窗口取 **T-1 及更早**。当天账单对不上是正常的。

## 一、部署拓扑

### 1.1 生产形态

```
reverse-proxy (nginx, 80/443 唯一入口)
    ├── /            → portal（Vue 静态页）
    ├── /api/        → control-plane（Spring MVC）
    └── /v1/         → gateway（Spring WebFlux）
                          ↓
                     PostgreSQL 17.6
    + backup 容器（每日 02:00 cron）
```

- **无 Redis**（ADR-0005）
- **无 LiteLLM/Bifrost 运行时**（ADR-0004）
- ⚠️ **仓库里没有 Prometheus / Grafana 服务，也没有对应 compose profile**（`compose.prod.yaml` 里唯一的 profile 是 `kafka`）。
  `deploy/grafana/miqrokey-dashboard.json` 是**给人导入外部 Grafana 的看板文件**。
  `/actuator/prometheus` 只在 Spring 的 `monitoring` profile 下暴露（`application-monitoring.yml`），**prod 栈没开它 → 默认 404**

### 1.2 两个 compose 文件

| 文件 | 用途 |
|---|---|
| `deploy/compose.yaml`（29 行） | **开发/本机**——只有基础设施 |
| `deploy/compose.prod.yaml`（280 行） | **生产**——portal + control-plane + gateway + postgres + backup + secrets-init |

> ⚠️ **`deploy/compose.yaml` 里没有前端**；portal 在 `compose.prod.yaml`。

### 1.3 容器镜像（4 个 Dockerfile）

`deploy/docker/` 下：`control-plane.Dockerfile`、`gateway.Dockerfile`、`portal.Dockerfile`、`backup.Dockerfile`

## 二、部署与升级

### 2.1 用 `deploy/deploy.sh`（**不要手工 docker build + up**）

`deploy/deploy.sh`（**589 行**）的头部注释解释了它为什么存在——**这是我实际踩过的三类故障**：

| 故障 | 现象 |
|---|---|
| (a) | 两个会话同时构建同一 tag → **"哪个镜像在跑"从机器状态上无法回答** |
| (b) | `up` 报成功但容器还跑着旧镜像 → **没有对比过运行容器与 tag** |
| (c) | 容器起来了、镜像对，但**配置错**（`.env` 没加载 → 每个变量静默回落到 compose 默认值 → 网关 403 拒绝自己的 origin，#794） |

所以 `deploy.sh` 的设计是：**持一把锁**，结束前**断言它能知道的**（运行容器 == 刚构建的镜像），并用 `--smoke-url` 断言**它不知道的**（真实客户端行为）。

> **没有 `--smoke-url` 时，收尾输出会说明"验证了什么/没验证什么"，而不是谎称"verified"。**

### 2.2 用法

```bash
deploy.sh --context DIR [--services "a b"] [--commit SHA] [--caller LABEL] \
          [--smoke-url URL] [--smoke-method METHOD] [--smoke-data BODY] \
          [--smoke-origin ORIGIN] [--smoke-expect PATTERN] \
          [--dry-run] [--verify-only]
```

- `--context`：**本次部署签出的副本目录**（含 backend/ frontend/ deploy/），**绝不是线上工作树**
- `--smoke-url`：真实客户端会问的请求；**不通过则整个部署失败**
- `--smoke-insecure`：自签证书时需要（**生产不要用**）

### 2.3 部署后必做：六步闭环冒烟

1. 注册用户
2. 加入项目
3. 建 Virtual Key
4. 真实推理（打一次 `/v1/messages`）
5. 用量核对（门户能看到刚产生的用量）
6. 对账/导出抽查

### 2.4 2G 演示机特别处理

- **JVM 限堆 + SerialGC + GC 日志**
- **portal 构建改串行** `typecheck` + `build`（并行时峰值内存 1.3G → 740MB，#667）
- `shared_buffers` 调优
- 详见 `docs/configuration-reference.md` 与 `docs/deployment-and-operations.md`

## 四、备份与恢复

### 4.1 备份链路（`deploy/backup/`）

```
每日 02:00 cron
  → miqrokey-backup.sh
      pg_dump → gzip → AES-256-CBC/PBKDF2 200k 加密
      → <时间戳>.sql.gz.enc + SHA-256 manifest
```

**保留策略**（`lib-retention.sh`）：最新 **7 个日备份** + 其余**每 ISO 周 1 个至多 4 周**
> ⚠️ #438 才把它修正为**真正的日历周语义**——之前实际窗口只有 11 天。

### 4.2 恢复

```bash
# ⚠️ 两个脚本都必须带位置参数（备份文件名），且需要环境变量 MIQROKEY_BACKUP_KEY_FILE
export MIQROKEY_BACKUP_KEY_FILE=/run/secrets/backup_key

miqrokey-verify.sh  <file.sql.gz.enc>              # 干跑校验（不改数据，先跑这个）
miqrokey-restore.sh <file.sql.gz.enc> [target-db]  # 用 --single-transaction 原子恢复
```

> 参数缺失会直接退出并打印 usage（`miqrokey-verify.sh:12-13`、`miqrokey-restore.sh:17,22-23` 的 `:?` 展开）。

- 脚本可**脱库测试**：`test-restore.sh`、`test-retention.sh`
- **每季度至少一次恢复演练**

### 4.3 关键原则

- **备份加密密钥必须与在线主密钥分离保管**
- **本机备份不防主机损坏**——重要数据需要异地副本
- 备份脚本所在的 `backup` 容器随 `compose.prod.yaml` 一起部署

## 五、密钥轮换（三类，操作不同）

### 5.1 HMAC Key（Virtual Key 签名）—— 🔴 **没有批量迁移，只能先重发**

> 🔴 **`reencrypt` 端点不适用于 HMAC key。** 它只重加密三张表里的 AES-GCM 密文
> （`CryptoReencryptionService.java:92`：`upstream_credential_versions` / `webhook_endpoints` / `mcp_services`），
> **一个字节都不碰 Virtual Key 的签名密钥环**。
>
> **HMAC 密钥环不可批量迁移**：Virtual Key 的摘要是单向的、原值不落库——
> **退役任一 HMAC 版本 = 该版本签发的全部 Virtual Key 当场失效，且无法重算。**
>
> **唯一可行顺序**：
> 1. 查出该版本签发的所有 Virtual Key；
> 2. **让这些 Key 全部完成重发**（用户重新签发下一代 Key）；
> 3. 确认没有存量依赖后，才退役旧版本。
>
> 详见 `docs/configuration-reference.md` §4.3 第 5 条、`docs/operations-runbook.md` §11。

### 5.2 Master Key（真实凭证加密）

- 走同一个 `reencrypt` 端点
- 🔴 **master key 丢失 = 真实凭证不可恢复**（AES-256-GCM，无后门）

### 5.3 上游真实凭证（供应商 API Key）

见 `docs/operations-runbook.md` §3。轮换后需**刷新路由快照**（控制面提交事务后会自动 `pg_notify`）。

### 5.4 管理密钥 / 消费者密钥到期

- `ADMIN_API_KEY_EXPIRING` 事件（规则 opt-in **默认关**）
- `CONSUMER_KEY_EXPIRING` 提醒
- 详情见 runbook §3b、§3c

## 七、故障排查手册

### 7.1 按 HTTP 状态码归因

| 状态码 | 来源 | 排查方向 |
|---|---|---|
| **401** | 本系统 | **凭据类型与端点不匹配**（见第〇章第 2 条）|
| **403** | 本系统授权层 | 查 error code 归因（不是上游问题）|
| **429** | **两类来源，先分清**：① 上游供应商限流 ② **本系统 REJECT 配额超限自产**（带 `quota_exceeded` 信封 + `Retry-After`） | 看错误信封类型：有 `quota_exceeded` = 本系统；否则是上游 |
| **502 `upstream_unavailable`** | 本系统 | 首字节超时（**不是 504**）|
| **504** | 本系统 | **只有 MCP 路径有**（`McpProxyController`）|
| 500（裸） | 本系统 | 整体超时等未包装异常 |

> ⚠️ **纠正常见误解**：LLM 路径**没有 504 信封**；首字节超时是 **502 `upstream_unavailable`**；整体超时是裸 500。

### 7.2 诊断陷阱（runbook §15 摘要）

- **同一状态码 ≠ 同一语义** —— 别用一个 403 就断定是同一问题
- **泛化兜底藏类别** —— 上游把具体错误吞成通用错误时，要看原始日志
- **别把未验证输入当事实** —— 客户端报的错误信息可能是它自己编的

（工程侧的姊妹篇是 `docs/debugging-traps.md`：CI/构建/测试方法/源码 revision）

### 7.3 常见故障速查

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 部署后 403 拒绝自己的 origin | `.env` 没加载（#794） | 用 `deploy.sh`（它会断言） |
| 容器起来但跑旧代码 | 镜像 tag 没更新 | 用 `deploy.sh`（它对比运行容器与 tag） |
| 网关起不来 | Kafka `bootstrap-servers` 为空串但被当"已配置"（#825） | 见该 issue 的修法 |
| 新一轮部署网关抢跑迁移（#846/#851） | 编排未等控制面 | 已修：编排等待控制面 + 快照「未就绪」分类 |
| usage 不落库 | 队列饱和 / drop | 看 drop 计数与告警（F07） |
| 自签证书下冒烟"通过" | 请求其实 TLS 就失败了，000 被归类为"天气" | 加 `--smoke-insecure`（#827） |

## 九、本地开发环境（`miqro-local/`）

> ⚠️ **`miqro-local/` 被 `.gitignore` 排除**，新 clone 不会有。**原机器上的副本已随机器清空。**
> **但你不需要它 —— 下面是重建方法。**

### 9.1 集成测试唯一可靠入口：`mvnw21.sh`

仓库的 `mvnw.cmd` 需要 `java` 在 cmd 的 PATH 上；这个 shim **绕过 cmd 直接用指定 JDK**。
用法：

```bash
bash miqro-local/mvnw21.sh -f backend/pom.xml -Pintegration verify
```

**重建**：建 `miqro-local/` 目录，把下面内容存成 `miqro-local/mvnw21.sh`：

```bash
#!/usr/bin/env bash
# Maven wrapper runner pinned to the project JDK 21 (Windows). Use for every
# backend Maven command in this repo (mvnw.cmd needs java on the cmd PATH;
# this shim bypasses cmd entirely).
# Usage: miqro-local/mvnw21.sh <maven args...>   e.g. -f backend/pom.xml -pl control-plane-app -am test
set -e
cd "$(dirname "$0")/.."
JAVA21="D:/programming/jdk-21.0.12.1+1/bin/java.exe"
ROOT="$(pwd -W 2>/dev/null || pwd)"
exec "$JAVA21" -classpath ".mvn/wrapper/maven-wrapper.jar" \
  "-Dmaven.multiModuleProjectDirectory=$ROOT/backend" \
  org.apache.maven.wrapper.MavenWrapperMain "$@"
```

> 🔴 **必须改第 8 行的 `JAVA21`** 为你自己机器上的 JDK 21 路径（`<你的 JDK 21 安装路径>/bin/java.exe`）。
> 如果你在 Linux / macOS 上，这个 shim 不需要 —— 直接用 `./mvnw` 即可。

### 9.2 常见问题

- **Docker Desktop 掉线 → testcontainers 假红**：先 `docker info` 探活
- **`npm run lint` 是只读检查**（`eslint . --max-warnings 0`）——从 #822（09-18）起已改成只报不改。
  会重写文件的是 **`npm run lint:fix`**（带 `--fix`）→ **Windows 上别对整树跑它**（会把 ~50 个文件的 CRLF 改成 LF）
- **前端 vitest 必须在 `frontend/` 目录运行**
- **后端端点变更后必跑 `npm --prefix frontend run gen:types` 并提交**（注意产出是 `src/types/generated.ts`）
- **OpenAPI 基线变更必须再生 `docs/openapi/openapi-3.1.json`** 并跑破坏性检查
