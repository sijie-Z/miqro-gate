### 0.2 数据面的四条铁律（代码里反复强调）

1. **热路径绝不阻塞**：所有 JDBC / 文件 / DNS 都必须切到 `credentialDecryptScheduler`

> 因此**异常路径（500 / 404）也会被计入**（#910 把计数点从 `doOnSuccess` 挪到了 `beforeCommit`）。
> 采集口径与 §7.3 `writeUsage` / §11.8 是同一批（#1000 前后的观测口径调整）。

> **接手人必知**：网关（`gateway-app`）**没有** Spring Security filter chain、没有 `HandlerInterceptor`、没有 `@ControllerAdvice`、

> 这就是为什么「改鉴权」必须改 `ProxyController`，而不是加一个 filter。
>
> 补充：全仓**有 3 个 `HandlerInterceptor`** —— `OriginInterceptor` / `CsrfInterceptor` / `RoleInterceptor`，
> 但**都属 control-plane（MVC 控制面）**，与「网关数据面不用拦截器」这个结论不冲突：
> `gateway-app` 内确实一个都没有。

`ProxyController` 的 `/v1/**` 兜底（`rejectUnsupported`，第 218-234 行）语义：
- 路径命中三个白名单之一但方法不是 POST → **405**，body 按协议分 Anthropic / OpenAI 两种形状（第 109-123 行常量）。
- 其他 `/v1/**` → **404**，用 OpenAI 形状（第 233 行）。

- `proxyRequest` 里的 try/catch 只接 `AuthFailureException`（`ProxyController.java:247-249`）—— 因为

### 1.3 SSE 流式请求有什么不同

判定点在 `ProxyController.java:545-546`：

```java
boolean isSse = upstreamResponse.headers().contentType()
        .filter(type -> type.isCompatibleWith(MediaType.TEXT_EVENT_STREAM)).isPresent();
```

| 方面 | 非流式 | 流式（SSE） |
|---|---|---|
| usage 来源 | `SseUsageObserver.parseUsageJson(objectMapper, collector.bytes())`（第 566 行，响应体 JSON） | `attempt.usageObserver.wrap(observed)` 逐事件观察（第 551 行） |
| 观察器 | 不挂 | `SseUsageObserver`（`SseUsageObserver.java:61-63`，`doOnNext` 旁路读，不改字节） |
| 缓冲 | 响应体整段落进 `BodyCollector` | 同样落 `BodyCollector`（用于缓存与 providerRequestId 提取），**超过 `maxProxyBufferBytes` 就 overflow 并放弃缓存**（第 991-995 行） |
| 超时 | 连接 / 首字节 / 整体 `responseTimeout` | 额外 `observed.timeout(properties.streamIdleTimeout())`（第 554 行，默认 5min，**每个 chunk 重置**） |
| 缓存填充 | 成功且未 overflow 且无 tool call → 缓存 | 同样条件（第 581-582 行）；SSE 响应**字节原样**存入并原样重放 |
| 客户端取消 | 少见 | 常见；`RequestStatus.CLIENT_CANCELLED`，且**不计入熔断**（第 500 行） |
| 响应头 | `X-MiQroKey-Request-Id`（缓存命中/miss 另加 `X-MiQroKey-Cache`） | 同左 |

**流式请求的真正风险**：一旦 `clientResponse.writeWith(observed)` 开始，HTTP 状态行和响应头**已经提交**。
此时若 stream-idle 超时或上游 mid-stream 断开，**网关无法再写任何错误信封**，只能断开连接；
这一事实反映在 `lifecycleStatus(...)`（第 760-782 行）：

```java
if (upstreamError != null) {
    if (isTimeout(upstreamError)) {
        return firstByteSeen ? STREAM_INTERRUPTED : TIMEOUT_BEFORE_FIRST_BYTE;
    }
    return firstByteSeen ? STREAM_INTERRUPTED : UPSTREAM_UNAVAILABLE;
}
```

`UPSTREAM_REJECTED`（非 2xx）与 `SUCCEEDED` 只在「body 完整收完」时产生。
`isTimeout()`（第 790-798 行）沿 cause 链找 `java.util.concurrent.TimeoutException` 或
`io.netty.handler.timeout.ReadTimeoutException`。

### 1.4 与 SseUsageObserver 的边界（安全相关）

## 2. 鉴权链

### 2.1 先纠正一个术语：本仓库**没有**「三级鉴权链（Visitor / API Key / …）」

通读仓库后确认：**「Visitor / API Key 三级鉴权链」不是网关自身对调用方的鉴权**，
而是 **MCP 上游后端（backend）的鉴权注入模式**：

- 需求编号 F64 / issue #320 / 腾讯 raw 03，见 `docs/feature-backlog.md:37`、`docs/progress.md:801`。
- 数据模型：`backend/domain/src/main/java/com/miqroera/miqrokey/domain/model/McpService.java:13`、`:86-87`
  （`backendAuthMode` 只能是 `VISITOR` 或 `API_KEY`）。
- 数据面实现：`McpProxyController.java:332-362`（`VISITOR` → 不注入任何 header；`API_KEY` → 解密快照密文并注入
  `Authorization: Bearer`）。
- 控制面 tools/list 同步实现：`McpToolSyncService#resolveBackendBearer`
  （`backend/control-plane-app/src/main/java/com/miqroera/miqrokey/controlplane/service/McpToolSyncService.java:154-172`）。

**数据面真正的调用方鉴权有三套，但它们是「分入口」的，不是「分级」的**：

| 入口 | 凭据 | 验证位置 |
|---|---|---|
| LLM 代理 `/v1/messages` 等 + `/v1/models` + `/v1/context-registry` | Virtual Key `mqk_live_…` | `VirtualKeyResolver`（gateway-app） |
| MCP 数据面 `/mcpservers/**` | 消费者 API Key `mqk_api_…` **或** 消费者 RS256 JWT | `McpProxyController#authenticate`（gateway-app） |
| 控制面 `/api/v1/billing/**` | 消费者 API Key `mqk_api_…` **或** 消费者 JWT | `ApiKeyAuthFilter`（control-plane-app） |
| 控制面 `/api/v1/admin-api/**` | 机器凭据 `mqk_admin_…` | `AdminApiKeyAuthFilter`（control-plane-app） |

> **接手人提示**：要改「鉴权」先确认改的是哪一套。文档里写「三级鉴权链」的地方，指的都是 MCP 上游 backend 鉴权，
> **不要**据此去改 `VirtualKeyResolver`。

### 2.2 Virtual Key（`mqk_live_`）验证 —— `VirtualKeyResolver`

**类**：`backend/gateway-app/src/main/java/com/miqroera/miqrokey/gateway/vkey/VirtualKeyResolver.java`
**职责**：热路径上的 Virtual Key 认证（全内存、无阻塞 I/O）。

**五步流水线**（类注释第 20-36 行，实现对应上面各方法）：

1. **凭据头**：`Authorization` / `x-api-key` / `api-key` 里必须**恰好一个**非空值。
   0 个 → 401 `unauthorized`（第 157-159 行）；多个 → 401 `unauthorized`（第 160-163 行）。
   `Bearer` 前缀大小写不敏感地剥掉；剥完为空 → 401（第 172-177 行）。
   ⚠️ 注意：`Bearer` 空 token 的判定**在 404 解析之前**，注释解释了原因（第 173-175 行）。
2. **格式解析**：`VirtualKeyParser.parse(presented)`（`backend/domain/.../vkey/VirtualKeyParser.java:52-101`）。
   格式 `mqk_live_<publicKeyId>_<secret>.<projectTag>`：
   - `publicKeyId` 固定 **22 字符**（base64url of 16 bytes）
   - 分隔符恰好一个 `_`
   - `secret` 固定 **43 字符**（base64url of 32 bytes）
   - `projectTag` 是最后一个 `.` 之后的部分，正则 `^[A-Za-z0-9_-]{1,64}$`
   - **位置式解析**（因为 base64url 字母表本身含 `_`），见 `VirtualKeyParser.java:15-23` 的说明。
   - `decodeStrict` 会重新编码比对，拒绝非规范 base64url（第 107-121 行）。
   - 任何畸形 → `VirtualKeyParseResult.invalid()`，**从不抛异常**。
3. **快照查表**：`snapshot.key(parsed.publicKeyId())`（`VirtualKeyResolver.java:121`）。未知 → 404。
4. **常量时间 HMAC 校验**：`crypto.validateConstantTime(publicKeyId, rawSecret, key.secretDigest(), tenantId)`
   （第 130-131 行）。详见 2.3。
5. **绑定解析（CAA ladder）**：`requestContextResolver.resolve(...)`（第 88 行）→ 详见 2.4。

**失败语义刻意的不可区分**：解析畸形 / key 不存在 / HMAC 不匹配 / 已吊销，全部返回 **404 `virtual_key_invalid`**
（第 185-187 行）。这是反枚举设计，注释在类注释第 38-41 行。

**内存擦除**：`resolve()` 在 `finally` 里 `SecretWiping.clearArray(parsed.rawSecret())`（第 92-94 行）；
`resolveIdentity()` 同样（第 112-114 行）。

### 2.3 HMAC 签名具体怎么做的

**类**：`backend/domain/src/main/java/com/miqroera/miqrokey/domain/crypto/impl/HmacVirtualKeyProvider.java`

```
digest  = HMAC-SHA-256(hmacKeyVersion, message)
```

租户 ID 进消息 ⇒ **A 租户创建的 key 永远无法在 B 租户通过校验**（类注释第 25-29 行）。

**多版本常量时间校验** —— `HmacVirtualKeyProvider.java:122-146`：

```java
boolean matched = false;
for (String version : hmacKeyRing.knownVersions()) {     // 遍历 ALL 版本，无提前退出
    byte[] key = hmacKeyRing.keyForVersion(version);
    if (key == null) continue;
    byte[] computed = hmacSha256(key, message);
    if (MessageDigest.isEqual(computed, expectedDigest)) {   // 常量时间比较
        matched = true;                                       // 累积，不 break
    }
    // finally: 擦除 key / computed
}
```

设计目的（类注释第 30-34 行）：**防止时序侧信道泄露"哪个版本匹配了"或"是否有版本匹配"**。
`MessageDigest.isEqual` 是常量时间比较；循环不提前退出。

**Key 长度约束**：HMAC key 最少 32 字节（第 43 行 `MIN_HMAC_KEY_BYTES`），构造时对 ring 内每个版本校验（第 69-79 行）。
digest 固定 32 字节（SHA-256）。

**格式化产物**（`generate`，第 83-108 行）：
- `publicKeyId` = base64url(SecureRandom 16 bytes)，无 padding
- `rawSecret` = SecureRandom 32 bytes
- `fullDisplayString` = `mqk_live_<publicKeyId>_<b64url(rawSecret)>[.<projectTag>]`
- `displayPrefix` = publicKeyId 前 8 字符；`lastFour` **取自无标签的 core**，避免标签污染展示的尾四位（第 91-96 行）
- `finally` 里擦除 hmacKey / message / rawSecret

**生产者调用方**：控制面 `VirtualKeyService`（`backend/control-plane-app/.../service/VirtualKeyService.java`）。
数据面**只读快照里的 digest**，从不生成。

#### (A) MCP 数据面：`McpProxyController#authenticate`

优先级（第 557-578 行）：

**两条定时线**：

1. **主刷新**：`refresh()`（第 80-95 行），`fixedDelay` 30s（`application.yml:45`）。
   - 先 `versionCounter.incrementAndGet()`（第 82 行）再 `loader.load(version, loadedAt)`（第 85 行），

   - 失败：如果是 `schema-not-ready` 走退避分支（第 89-92 行）；**其他任何失败只 ERROR 日志，保留旧快照**（第 93 行）。
2. **未就绪重试 ticker**：`retryWhenSchemaNotReady()`（第 101-106 行），`fixedDelay` 2s
   （`application.yml:50`，`MIQROKEY_GATEWAY_ROUTE_RETRY_CHECK_INTERVAL`）。
   只在 `schemaNotReady == true` 且已过 `nextAttemptAt` 时才真正 `refresh()`。健康时每次只做一次原子读。

**「未就绪」是什么**（类注释第 28-40 行）：全新部署时网关可能先于控制面 Flyway 迁移完成而启动
（空库上 postgres 也报健康）。此时首次刷新会以 PostgreSQL `42P01`（`undefined_table`）失败 —— 这不是缺陷，
而是「还没建好」。分类逻辑：

```java
private static final String UNDEFINED_TABLE = "42P01";     // :50
static boolean isSchemaNotReady(Throwable failure) {       // :140
    for (Throwable t = failure; t != null; t = t.getCause()) {
        if (t instanceof SQLException sql && UNDEFINED_TABLE.equals(sql.getSQLState())) return true;
    }
    return false;
}
```

沿 cause 链走是因为 Spring 会把 `SQLException` 包进 `DataAccessException`。

**退避序列**：`retryBackoffSeconds(attempt)`（第 129-132 行）= `min(1 << min(max(attempt,1),5), 30)`
→ **2, 4, 8, 16, 30, 30, …** 秒（上限 30s，永不慢于正常刷新间隔，第 56 行注释）。
`deferUntilSchemaReady` 里设 `nextAttemptAt`（第 111 行）并 WARN（第 113-115 行）；
`clearNotReady()`（第 121-126 行）在恢复时 INFO 输出尝试次数。

**其他「降级」路径**：

- 单次刷新失败 → 保留旧快照继续路由（`RouteSnapshotHolder` 类注释第 14-20 行）。
- 版本回退 → `install()` 只 WARN 不拒绝（`RouteSnapshotHolder.java:46-49`）。
- **persistence 完全关闭时**：`GatewayFeatureConfig.emptyRouteSnapshotProvider()`（`GatewayFeatureConfig.java:51-54`）
  提供一个永远空的快照 —— **fail closed，每个 key 都是未知 → 全 404**。

### 4.4 轮换（master key rotation）实际操作流程

**代码支持的机制**：

1. `EncryptedSecret` 携带 `keyVersion`（`backend/domain/.../crypto/EncryptedSecret.java`），
   每行密文自描述用哪个版本加密的。
2. `decrypt` 按密文里的 `keyVersion` 取 key（`AesGcmEncryptionProvider.java:97`），
   **所以旧密文在轮换后仍可读**（未知版本才报 `CRYPTO_KEY_002`，第 98-101 行）。
3. `encrypt` 永远用 `activeKey()`（第 81 行）。
4. `reEncrypt(encrypted, tenantId, credentialId)`（第 111-118 行）：先按旧版本解密、再用新 active 版本加密、
   `finally` 擦除中间明文。这是**重加密工具方法**。

**类注释给出的轮换顺序**（`CryptoConfig.java:35-37` 原文）：
> 旧版本保留在 map 里供解密/校验；新加密永远用 active 版本。
> **加一个新版本 → 部署 → 重加密 → 移除旧版本 → 重启。**

配置上就是往 `miqrokey.crypto.encryption.versions` 里加 `v2: /path/key-v2` 并把
`active-version` 改成 `v2`，此时 `knownVersions()` 同时含 v1/v2；旧密文继续可读。

**控制面侧的重加密服务**：`CryptoReencryptionService`
（`backend/control-plane-app/src/main/java/com/miqroera/miqrokey/controlplane/service/CryptoReencryptionService.java`），
使用 `KeyEncryptionProvider#reEncrypt`。

**HMAC 侧的轮换是另一套语义**：Virtual Key 摘要可以跨版本校验，
`HmacVirtualKeyProvider#validateConstantTime` 遍历所有版本（第 126 行），
所以**轮换 HMAC key 不会让已发放的 Virtual Key 立即失效** —— 但新 key 会用新版本计算摘要。
注意 `computeDigest`（第 150-159 行）只用 active key，所以**轮换后新生成的 key 摘要版本不同，
但校验端仍能通过**。

**MCP 上游后端凭证的加解密**：与 LLM 凭证同一套 provider（`AesGcmEncryptionProvider`），
但 AAD 里的 `credentialId` 传的是 **MCP service id**：
`McpProxyController.java:349` → `crypto.decrypt(encrypted, service.tenantId(), service.id())`。
控制面写入侧同样（`McpToolSyncService` 解密用 `(tenantId, serviceId)`）。

> ⚠️ `RetentionSidecar` 用的是第三个约定：AAD 里的 credentialId 位置传一个**合成的常量**，
> 见 `RetentionSidecar.java:43-48` 注释 —— 这个常量永远不匹配任何真实 credential。

### 5.4 数据面怎么用适配器（`ProxyController.resolveTarget`）

`ProxyController.java:887-924`：

```java
private ResolvedTarget resolveTarget(ServerWebExchange exchange, AuthContext ctx,
        CredentialInjector.InjectedCredential cred, String wireProtocol) {
    String productCode = ctx.snapshot().productCode(ctx.binding().productId());        // :889
    if (productCode != null && providerCatalog.findById(productCode).isPresent()) {    // :890  ← 签名目录门
        ProviderProductAdapter adapter = adapterRegistry.findById(productCode).orElse(null);   // :891
        if (adapter != null) {
            ProtocolFamily family = ProtocolFamily.valueOf(wireProtocol);
            RouteSnapshot.CredentialRecord credential = ctx.snapshot().credential(ctx.binding().credentialId());
            URI baseUrl = credential != null ? credential.baseUrl(family.name()) : null;   // :895  按协议族取 base
            if (baseUrl != null && "https".equalsIgnoreCase(baseUrl.getScheme())) {        // :899  仅 https 走 adapter
                try {
                    var request = exchange.getRequest();
                    RouteContext route = new RouteContext(ctx.key().tenantId(), ctx.binding().productId(),
                            ctx.binding().projectId(), family, baseUrl);                    // :902
                    InboundRequest inbound = new InboundRequest(request.getMethod().name(),
                            request.getURI().getPath(), decodeQuery(request.getURI().getRawQuery()),
                            request.getHeaders());                                          // :904
                    TargetRequest target = adapter.resolve(route, inbound);                 // :907
                    StringBuilder sb = new StringBuilder(target.origin().toString());
                    sb.append(target.path());
                    if (target.query() != null && !target.query().isEmpty()) {
                        sb.append('?').append(target.query());
                    }
                    return new ResolvedTarget(URI.create(sb.toString()), target.headers());  // :913
                } catch (RuntimeException e) {
                    // 适配器坏了绝不能拖垮中继：回落到 legacy splice + WARN
                    log.warn("Adapter target resolution failed (product={}): {}; using single base",
                            productCode, e.getMessage());
                }
            }
        }
    }
    return new ResolvedTarget(buildUpstreamUri(exchange, cred.baseUrl()), null);            // :923  legacy 路径
}
```

**三条关键设计**：

1. **产品必须同时存在于签名目录与注册表**才走 adapter（第 890-891 行双重检查）。
2. **只有 https base 才走 adapter**（第 899 行）—— 因为 `RouteContext` 的构造器强制 https（SPI 级 SSRF 边界）；
   plain-http 上游（本地 mock、`allowed-cidrs` 私网部署）走 legacy verbatim splice（第 923 行）。
3. **适配器抛异常会静默降级**为 legacy splice（第 914-919 行）—— 适配器 bug 不会打挂网关，但只留一条 WARN。

**legacy splice**（第 953-965 行）：`baseUrl` 去掉尾部 `/` + `request.getRawPath()` + `?rawQuery`，
**保留原始 query 字节不做解码**。注意此时返回的 `ResolvedTarget.headers()` 为 `null`，
于是 `forwardWithResolvedCredential` 走 `HeaderFilters.filterInboundHeaders(exchange.getRequest().getHeaders())`
分支（第 438 行）。

### 6.3 什么情况下不缓存

**入口判据**：`CacheEligibility.isCacheable(...)`（`backend/gateway-app/.../proxy/CacheEligibility.java:29-33`）

```java

        boolean hasToolFields) {
    return "ENABLED".equals(ctx.key().cachePolicy())      // ① key 的 cachePolicy 必须是 ENABLED
            && "1".equals(cacheableHeaderValue)           // ② 客户端显式声明 X-MiQroKey-Cacheable: 1
            && !hasToolFields                             // ③ body 不含 tools / tool_choice
            && body != null && body.length > 0;           // ④ body 非空
}
```

`hasToolFields` 在 `ProxyController.java:262` 计算：`root.has("tools") || root.has("tool_choice")`。

**响应侧不缓存的额外条件**（`ProxyController.java:581-582`）：

```java

        && !attempt.collector.containsToolCall();
```

- `successful` = 2xx（第 569 行）
- `overflow` = 响应体超过 `maxProxyBufferBytes`（默认 256KB），见 `BodyCollector.append`（第 986-1001 行）
- `containsToolCall()` = 响应字节里含 `"tool_calls"` 或 `"tool_use"`（第 1016-1022 行，纯字节扫描启发式，
  误判只会少缓存）

**缓存完全不生效的场景**：`miqrokey.cache.enabled=false`（默认）→ `NoopCacheProvider`；
或 `miqrokey.gateway.persistence.enabled=false` → L2 拿不到 DataSource（`CacheConfig.java:41`）；
或 key 的 `cachePolicy != ENABLED`。

**缓存写入是 best-effort 且在调度器上**（`ProxyController.java:587-595`）：

```java
Mono.fromRunnable(() -> responseCache.put(...))
    .subscribeOn(credentialDecryptScheduler)
    .subscribe(null, error -> log.warn("aigw.cache.put_failed: {}", error.getMessage()));
```

数据库写失败**只记日志**（客户端早已拿到响应）。

**缓存读取也在调度器上**（第 311-313 行）：L2 命中要走 PostgreSQL，注释明确写了
"the cache lookup is blocking I/O ... must never run on the event loop"（第 308-310 行）。

**L2 的 SQL 行为**（`PostgresCacheProvider.java`）：
- 读（第 46-74 行）：`WHERE tenant_id = :tenantId AND cache_key = :cacheKey
  AND (expires_at IS NULL OR expires_at > now()) LIMIT 1`；**解析失败视为 miss**（第 70-73 行）
- 写（第 77-120 行）：`INSERT ... ON CONFLICT (tenant_id, cache_key) DO UPDATE SET ...`，
  **`hit_count` 不被覆写**（第 108 行注释）
- 失效（第 122-126 行）：`DELETE FROM cache_entry WHERE tenant_id = ... AND project_id = ...`

### 6.4 缓存命中如何影响用量统计

**命中时的行为链**：

- 缓存节省 `savedByGatewayCache` 按**该组命中中最晚一次的时刻**取价目 —— 这是近似，

- `cache_hit_event` 是**秒级去重**计数，对同秒密集重复命中是低估口径（第 193 行）。
- 三张表计数单位不同，**不得相加或互换**（第 194 行）：

### 7.4 怎么入队、怎么落库

**入队（`PostgresUsageEventBus`）** —— `backend/queue-spi/src/main/java/com/miqroera/miqrokey/queue/PostgresUsageEventBus.java`

```java
private void offer(Object event)                       // :133   热路径唯一入口
private boolean writeThrough(Object event)             // :162   WRITE_THROUGH 模式的应急单条写
@Scheduled(...flush-interval:1s) public void scheduledFlush()        // :204
@Scheduled(...flush-interval:1s) public void scheduledSignalReport() // :236
private void reportSignal(long delta)                  // :259
public void flush()                                    // :272   完全排空
private boolean flushChunk()                           // :288   一批 drain + write
public QueueMetrics metrics()                          // :332
```

**队列本身**：`new ArrayBlockingQueue<>(capacity)`（第 102 行），容量默认 **50000**
（`application.yml:53`，`MIQROKEY_GATEWAY_QUEUE_CAPACITY`）。

**`offer` 的行为**（第 133-144 行）：

```java
if (queue.offer(event)) { totalPublished.incrementAndGet(); return; }
if (saturationMode == SaturationMode.WRITE_THROUGH && writeThrough(event)) return;
totalDropped.incrementAndGet();
sampleHighWater();
log.warn("Usage event bus saturated; event dropped. queued={} mode={}", queue.size(), saturationMode);
```

**`WRITE_THROUGH` 的语义**（第 162-182 行）：把单条事件交给专用 writer executor，
等待 `writeThroughTimeout`（默认 5s，`QueueConfig.java:126`）内的幂等写入。
**发布线程会有界阻塞，但绝不自己执行 JDBC**（第 158-160 行注释）。
超时或失败 → 返回 false → 调用方照常计 drop。

**flush 是「完全排空 + 分批」**（第 272-282 行 + 第 288-329 行）：

```java
public void flush() { while (flushChunk()) { /* keep draining */ } }
```

`flushChunk()` 每次 `queue.drainTo(drained, flushThreshold)`（第 290 行）——
`flushThreshold`（默认 100）是**批大小，不是排空上限**。
注释记录了这个 bug 的历史（#417）：之前单批 drain 让稳态吞吐被限制在 `100/5s = 20 events/s`，
远低于红线压测的 ~2400 events/s，导致有界队列饱和、DROP 模式丢掉了大部分用量事件（第 273-277 行）。
`flush-interval` 也从 5s 调到了 1s（#424，`application.yml:55`）。

**失败重入队**（第 317-328 行）：`writeBatch` 抛异常时**按原顺序重新 offer**，
放不下的计 drop，并 `return false` 停止本轮（不空转），下轮再试。
**写入是幂等的，所以重试不会重复计数**（第 52-53 行注释）。

**线程模型**（第 41-48 行注释）：`scheduledFlush` 跑在 Spring 调度线程，
只负责 `writerScheduler.schedule(() -> flush())`；真正的 JDBC 跑在专用
boundedElastic（`usage-writer`，默认 4 线程，`QueueConfig.java:78-81`）。
`flushing` 这个 `AtomicBoolean` 是**在途保护**，跳过重叠 flush（第 206 行）。
注意第 215-221 行的细节：**调度被拒绝时必须复位 `flushing`**，否则所有后续 flush 会永久停摆（#424）。

**落库（`PostgresUsageEventWriter`）** —— 一个事务处理整批（`writeBatch`，第 44-72 行）：

| 方法 | 行号 | SQL 要点 |
|---|---|---|
| `writeUsage` | 74-138 | `INSERT INTO usage_event (...) VALUES (...) ON CONFLICT DO NOTHING`（**第 142 行**）—— 裸 `ON CONFLICT DO NOTHING`；建在 `(tenant_id, provider_request_id)` 上的那个部分唯一索引**还在**，但**已不再是仲裁者**（#887 改的） |
| `writeContextEvidence` | 153-162 | `INSERT INTO request_context_evidence (...) ON CONFLICT (id) DO NOTHING`（第 160 行） |
| `writeHits` | 206-233 | `INSERT INTO cache_hit_event ... ON CONFLICT (tenant_id, cache_key, level, occurred_at) DO NOTHING`（第 225 行）+ `UPDATE cache_entry SET hit_count_l1/l2 = ... + 1`（第 227-232 行） |
| `writeStarted` | 239-269 | `INSERT INTO request_usage_records (...) ON CONFLICT (started_at, gateway_request_id) DO NOTHING`（第 267 行），`request_status = 'IN_FLIGHT'` |
| `writeCompleted` | 278-339 | `INSERT ... ON CONFLICT (started_at, gateway_request_id) DO UPDATE SET ... WHERE request_usage_records.request_status = 'IN_FLIGHT'`（第 316-337 行） |

**`writeCompleted` 的守卫语义**（第 271-277 行注释）：
- 只把 `IN_FLIGHT` 行流转到终态 —— **已终结的记录永不被覆写**，重试的 flush 不会二次终结。
- 如果 start 行从未落库（例如 start 被 drop 了），completion 会**插入一条独立的终态行**
  （因为事件自带完整快照）。
- `upsert` 只更新业务字段，`id` / `started_at` 不变。

**`writeUsage` 里还有一个单条丢弃**（第 78-87 行）：`modelId == null` 的事件被**单条丢弃并 WARN**，
而不是让整批失败 —— 这是第 7.3 节那个 skip 的第二道防线。

### 7.5 为什么用队列（而不是同步写库）

代码注释与配置给出的理由：

1. **热路径不能阻塞**（`UsageEventBus.java:11-15` 类注释：*"The gateway hot path only enqueues — never writes
   to the database synchronously"*）。
2. **批量摊薄 JDBC 开销**：一次 flush 一个事务、一个 `batchUpdate`（第 44-72 行）。
3. **数据库抖动不放大成请求失败**：写失败重入队，下一轮再写（第 50-53 行注释）。
4. **关闭时兜底**：`QueueConfig.java:88` 的 `@Bean(destroyMethod = "flush")` —— 优雅关机时把队列刷完。
   注释记录了这个 bug（#451）：以前每次重启/部署会丢掉最多一个 flush 周期的已接受事件，**而且不计入 dropped**。
   测试：`backend/gateway-app/src/test/java/com/miqroera/miqrokey/queue/UsageBusShutdownFlushWiringTest.java`。

### 7.6 drop 计数怎么暴露（两条通道）

**通道一：Micrometer Gauge（进程内）** —— `backend/gateway-app/src/main/java/com/miqroera/miqrokey/gateway/config/QueueMetricsBinder.java:18-31`

**通道二：持久化 drop 事实（跨进程告警）** —— 这是 F07 / #245 加的能力，
因为「进程内计数器没有任何运维能查到」（`PostgresUsageEventBus.java:55-62` 注释）：

- `scheduledSignalReport()`（第 236-254 行）与 flush 同频（1s）：
  取 `totalDropped` 与 `reportedDropped` 的差值；**delta <= 0 直接返回**（健康网关一行都不写）；
  用 `compareAndSet` 原子认领从 `reportedDropped` 到 `observed` 的迁移。
- `reportSignal(delta)`（第 259-269 行）在 writer executor 上写一条 `gateway_queue_signal` 行；
  **写失败则 `reportedDropped.addAndGet(-delta)` 把 delta 还回去**，下轮一起报（第 263-268 行）。
- **调度被拒绝**（writer 队列饱和 / executor 已 dispose）时同样把 delta 还回去并 WARN（第 246-253 行）——
  注释明确说"must not swallow the loss"。
- 落库：`PostgresQueueSignalWriter.writeSignal`（`.../queue/PostgresQueueSignalWriter.java:37-54`），

  `id` 是**每次随机 UUID**（不是确定性键）—— 因为重试靠「bus 恢复未写 delta」驱动，回滚的事务不会留下可碰撞的行
  （类注释第 13-19 行）。
- **信号归到种子租户** `SIGNAL_TENANT_ID = 00000000-0000-0000-0000-000000000001`
  （第 79 行）；类注释第 70-78 行解释了为什么：队列是进程资源不是请求资源，
  评估器按租户过滤告警规则，所以只有平台级规则会触发；其他租户的规则聚合到恒为 0 的窗口，保持安静。
- **`WRITE_THROUGH` 模式不产生 drop 信号**（`QueueSignal.java:22-26` 注释）：
  该模式是拿延迟换不丢，事件最终仍被持久化。

**`sampleHighWater()`**（第 151-153 行）：**只在 drop 路径上采样**（`queuedHighWater` 取 max），
健康路径零开销。注释解释了为什么不常采样：唯一有意义的时刻就是溢出那一刻（第 148-150 行）。

**`InMemoryUsageEventBus`**（`.../queue/InMemoryUsageEventBus.java`）：
persistence 关闭时的回落（`QueueConfig.java:98-102`，`@ConditionalOnMissingBean`），
`LinkedBlockingQueue`，只累加 `totalDropped`，提供 `usageEvents()` / `hitEvents()` / `startedEvents()` /

**服务级 vs Tool 级重试的区别**（问题 10 的一部分）：

| 维度 | 服务级 | Tool 级 |
|---|---|---|
| 数据来源 | `mcp_resilience_policy`（V30） | `mcp_tool_retry_policy`（V46，issue #360） |
| 作用范围 | 该 MCP 服务的**所有**调用 | 仅 `tools/call` 命中该工具时 |
| 合并方式 | 基础策略 | `servicePolicy.withRetry(tool.retry())` 只替换 retry 字段（`McpProxyController.java:328-330`） |
| 熔断 | **始终服务级**：`policy.breakerSkipRetry()` 与 `breaker` 实例都用服务的 | 工具级没有独立熔断策略 |
| 桶键 | `bucketFor(toolName, rpcMethod)`：`tools/call` 按**工具名**，其他信封方法按**方法名**，其余归 `"envelope"` | 同左（桶是熔断的粒度，不是策略的粒度） |

**桶键设计**（`bucketFor`，第 643-648 行；`ENVELOPE_METHODS` 常量第 631-633 行）：

```java
private static final Set<String> ENVELOPE_METHODS = Set.of("initialize", "ping", "tools/list", "tools/call",
        "prompts/list", "prompts/get", "resources/list", "resources/read", "resources/subscribe",
        "resources/templates/list", "resources/unsubscribe", "completion/complete", "logging/setLevel");

static String bucketFor(String toolName, String rpcMethod) {
    if (toolName != null) return toolName;
    return rpcMethod != null && ENVELOPE_METHODS.contains(rpcMethod) ? rpcMethod : "envelope";
}
```

**为什么要有这个白名单**（第 636-642 行注释，#727）：以前任何客户端提供的 `method` 字符串都会成为
一个**永不淘汰的桶**，注册表可以无限增长。加了固定集合后，
注册表大小真正被 `services × tools + methods` 界住（`McpCircuitBreakerRegistry` 类注释第 17-18 行）。

### 9.3 ⚠️ 关于 `503 circuit_open` 与 `504 超时信封` 的**重要事实核查**

**问题 9 的前提需要修正**：

**(a) LLM 数据面没有 504 信封。** 全仓 grep `GATEWAY_TIMEOUT`/`504` 在 `gateway-app/src/main` 命中 **3 处**：
- `LlmCircuitBreakerProperties.java:41` —— 默认错误状态码集合 `Set.of(500,502,503,504)`（熔断计数用）
- `McpProxyController.java:472` —— MCP 的 `mcp_upstream_timeout`

`ProxyController` 的 `onErrorResume` **接三类**（第 343-350 行）：
`AuthFailureException`(:343)、`WebClientRequestException`(:344)、**`PrematureCloseException` → `upstreamClosedBeforeFirstByte`(:348)**；
外层链还有第四个 `DataBufferLimitException`(:349-350)。
> ⚠️ `PrematureCloseException` 这一类是后补的——代码注释(:340-342)写明「premature close 以前漏成 500，才补的类型化处理」。

```java
pipeline.onErrorResume(AuthFailureException.class, e -> writeError(exchange, e))
        .onErrorResume(WebClientRequestException.class,
                e -> writeError(exchange, new AuthFailureException(HttpStatus.BAD_GATEWAY, "upstream_unavailable",
                        "Upstream provider is unreachable")));
```

于是：
- **首字节超时**（reactor-netty `responseTimeout`，`ProxyConfig.java:38`）抛出的
  `ReadTimeoutException` 被 WebClient 包成 `WebClientRequestException`
  → 落到第 325 行 → 客户端看到 **502 `upstream_unavailable`**。
  **集成测试印证**：`TimeoutRetryIntegrationTest.java:210` 断言 `.expectStatus().isEqualTo(502)`，
  同文件 `:176` 也是 502；测试同时断言 `request_status = TIMEOUT_BEFORE_FIRST_BYTE`（第 215 行）。
- **整体响应超时**（`properties.responseTimeout()`，默认 10min，`ProxyController.java:472` 的 `.timeout(...)`）
  抛出的是裸 `java.util.concurrent.TimeoutException`，**不匹配任何一个 onErrorResume**
  → 冒泡到 WebFlux 默认错误处理 → **HTTP 500 + Spring 默认 body**（不是网关信封）。
  这只在响应头尚未提交时可见；若流已开始，连接直接断。
- **stream-idle 超时**（第 554 行）几乎总是在响应头已提交后触发 → 无法写任何信封，连接断开，
  生命周期记为 `STREAM_INTERRUPTED`。

**(b) MCP 的 504 是真实的**，`McpProxyController.java:463-474`，语义是「per-service 上游预算耗尽」
（I20 / doc 135906「超时时间」），与 LLM 侧的连接/首字节/整体三类超时不是一回事。

**(c) 文档口径**：MCP 的 504 写在 `docs/api-contract.md:964`；LLM 熔断的 503 `circuit_open` 写在 `:1271`。
**没有任何文档声称 LLM 路径有 504 信封**（已核实）。
所以这是「问题前提与代码不符」，而不是「代码与文档不符」。

**(d) 429 语义**（问题 9 的第三项）：`QuotaGate`（`QuotaGate.java:20-29`）是**唯一的 429 来源**，
语义是「控制面评估器判定该 user/project 作用域命中某条 `REJECT` 配额规则」，
是**软着陆**（ADR-0020）：key 不失效、不自动禁用；跨入新窗口或提高限额后判定自然消失。
必须带 `Retry-After`（第 872-874 行写出）。
判定数据来源 `quota_enforcement` 表 → `JdbcRouteSnapshotLoader.loadQuotaEnforcement()`（第 95-105 行）
→ `RouteSnapshot.quotaBlocked*`（第 103-123 行）。
**注意**：网关侧**没有**速率限制（rate limit）实现，429 只表示配额硬阻断。

### 11.3 `ProviderProductAdapter#createUsageObserver` 的契约与数据面实现不符

接口注释（`provider-spi/.../spi/ProviderProductAdapter.java:49-52`）：
*"Called once per request before the upstream exchange"*。
但 `ProxyController` 的热路径**从不调用它** —— `UpstreamAttempt` 直接 new 内建的
`SseUsageObserver`（`ProxyController.java:622`）。
每个供应商的 `XxxUsageObserver` 目前只被控制面 / 适配器内部使用。
`docs/provider-adapter-contract.md:35` 把 `createUsageObserver` 列为必需方法，读者会以为数据面在用它。

### 11.4 生命周期事件与「用量事件」的触发时机不对称

`publishUsageEvent` 在 `writeWith(...).then(supplier)` 内（`ProxyController.java:559-571`），
即**只有响应完全写完才发**；而 `publishLifecycleComplete` 在 `doFinally`（第 478-512 行），
**任何终态都发**。类注释承认了这点（第 380-381 行：*"usage events themselves are only emitted for
fully completed requests"*）。后果：**客户端取消的请求有生命周期行、但没有 usage 行** ——
做对账时两张表的行数天然不等（`docs/usage-accounting.md:191-194` 也确认了这点）。

### 11.5 `RouteSnapshot.consumersByDigest` 字段名与内容不符

字段名与访问器叫 `consumerByDigest`（`RouteSnapshot.java:55, 355-362`），
但装载时用的键是 **consumer id 的字符串**（`JdbcRouteSnapshotLoader.java:321-322`：
`byDigest.putIfAbsent(id.toString(), new ConsumerRecord(...))`）。
功能上没问题（访问器是遍历值集合 + `MessageDigest.isEqual`，O(n) 线性扫描），
但名字会误导人以为它是 O(1) 的摘要索引。数据量大时这是性能隐患。

### 11.6 `QueueSignal` / 丢弃信号只在 DROP 模式产生

`QueueSignal.java:22-26` 与 `PostgresUsageEventBus.java:133-144` 一致：
`WRITE_THROUGH` 模式下事件最终被持久化，**不产生 drop 信号**。
运维看 `gateway_queue_signal` 表时要意识到：**表里没有行不代表没有饱和**，
只代表「要么没饱和，要么饱和了但被 write-through 兜住（此时发布线程有界停顿）」。
进程内 Gauge `miqrokey.usage.queue.dropped.total` 同样只在 DROP 路径自增。

### 11.7 `mcp_access_log` 没有保留策略

见 8.6 末尾。管理端查询窗口（≤31 天 / limit ≤1000）是唯一边界，**表会无限增长**。
对比之下 `request_usage_records` / `usage_event` 有 retention 与 sweeper。**接手后建议优先补这个**。

### 11.8 `GatewayMetricsFilter` 没有显式 order

它只实现 `WebFilter`，未实现 `Ordered`，所以是 `LOWEST_PRECEDENCE`。
当前只有一个 WebFilter 所以无影响；**但将来新增任何 WebFilter 而忘记设 order，计数归属就可能变**
（它靠 `exchange.getResponse().beforeCommit(...)` 在响应提交前读 `getStatusCode()`）。
计数点在 `beforeCommit` 意味着**异常路径（500 / 404）也会计入** —— 修 order 问题时要把这个行为差异一并考虑。

### 11.9 `docs/architecture.md` §10 的描述与代码的细微差异

`docs/architecture.md` 第 196-206 行描述 MCP 时写「F12/F13 韧性（首字节前重试 + 熔断 503）同管线」，
方向正确；但没提 `breakerSkipRetry=false` 时熔断**只观测不限流**这一模式
（代码在 `McpProxyController.java:409-414`，文档在 `docs/api-contract.md:1126` 才写清楚）。

### 11.10 LLM 路径缺少 504 信封（见 9.3）

不是文档错，而是**能力缺口**：整体响应超时（`responseTimeout`）会以裸 500 冒泡。
如果产品上需要「网关侧超时 → 504」，这是一个明确的待办。

### 12.4 三条最容易踩的坑（TL;DR）

1. **改鉴权不要加 filter** —— 网关没有 filter 链，鉴权写在 `ProxyController.proxyRequest` + `VirtualKeyResolver` 里。
2. **LLM 路径没有 504 信封** —— 首字节超时是 **502 `upstream_unavailable`**，
   整体超时是**裸 500**（见 9.3）；只有 MCP 有 `504 mcp_upstream_timeout`。
3. **「三级鉴权链 Visitor / API Key」是 MCP 上游 backend 鉴权，不是网关对调用方的鉴权**（见 2.1）。
