## 0. 需求原始语境（leader × 平台 leader 沟通要点，2026-09 转述，逐条保留）

1. 平台侧关心本网关部署的**带宽/请求量级**（用于 Kafka 容量与消费端部署设计）。
2. **内容留痕**：用户请求（问题/对话内容）需要能被保存并**按用户追溯**（例如
   "说了不合适的言论"的合规审计场景）。定位=**冷数据**；倾向**加密**（不是人人可读）。
   存储目标未定：候选 = 对象存储（S3 类）/ 平台本地文件 / 数据库。
3. **写入链路**：请求事件先投 **Kafka**（多请求、高吞吐；平台侧消费端可能是
   **多进程**，需要一个消息队列解耦），消费者负责持久化（落到数据库或文件；
   "也可以考虑消费者写到文件里、在本地服务上"）。
4. **用户身份映射（无感同步）**：虚拟 Key/用户身份会经 **OAuth** 让用户不感知地
   同步到平台侧（"这个后面平台那边会改"）——即平台登录/授权流里把
   `sub`/`user_id` 映射成本网关用户；本系统**自己的用户登录思路保持不变**（本地
   账号体系不动，F32 映射在此之上叠加）。

5. 语境备注："他们说用户不会察觉"——终端用户无感是产品预期，不是技术约束。

## 0c. 设计补强（v3 落地项，源自 M2/M10）

1) **网关本地缓冲（first-class）**：启用留痕时，事件先入进程内**有界队列**；队列
   满或 Kafka 不可达 → 落**本地暂存文件**（按小时/大小滚动，磁盘配额可配）；
   Kafka 恢复后补投（at-least-once + 事件幂等键）。缓冲不阻塞推理热路径（默认
   drop+计数；严格模式可选）。
2) **消费端输出目标（三选一或组合，配置驱动）**：对象存储（主，SSE-KMS）／平台
   本地文件（按 user 分目录分文件滚动）／平台侧数据库；文件与对象存储路径布局
   均为 `<bucket|dir>/tenant/<yyyy-mm-dd>/<user_hash>/<event>.enc`，便于按用户
   生命周期清理与检索。

## 1. 与既有决策/红线的冲突（必须显式承认）

- CLAUDE.md 产品红线：不保存 prompt/代码/工具正文/模型回答；日志不含正文；透明
  代理不读不改写正文。**本 ADR 的 R1 直接放宽该红线**（新增"合规留痕"例外通道）。
- 缓解设计（不放宽不彻底）：留痕为**独立、默认关闭**的可配置通道；只在启用后把
  「用户消息正文 + 审计元数据」做成**密文信封**落事件流；模型回复/工具正文默认不
  存（可扩展）；启用/范围/保留期由部署方配置并记审计；控制面与既有审计链不受影响。
- 需要所有者明确同意的三个放宽点：① 正文可被采集；② 采集内容加密存储后可被平台
  侧受权方读取；③ 网关/平台之间传输该密文事件。

## 2. 云厂商做法参照（已核实）

- 阿里云百炼：异步任务完成等事件 → **事件总线 EventBridge**（默认总线）→ 目标为
  HTTP 回调或 **RocketMQ**；计费/用量走查询接口，不推正文。内容安全（Green）做
  **检测与处置**，不是全量留底。
- 腾讯 AI 网关：事件驱动通知走 Webhook（本仓库 F03 同语义已实现）；MCP 元数据日志
  `aigw.mcp.*` 明确**不存正文**（raw 16）。
- **主流做法锚点（v2 默认值出处，阿里/腾讯为准）**：
  1) 事件管道：腾讯云 **CKafka**（Apache Kafka 协议兼容）与阿里云 **Kafka/MSE**、
     RocketMQ/EventBridge 均为"消息队列即事件管道"主流 → 我们选型=标准 Kafka
     协议，topic 按 user hash 分区保序，便于平台既有消费端互通。
  2) 冷数据存储：阿里 OSS / 腾讯 COS（兼容 S3 协议）是冷数据与合规留存的主流落点，
     配 **SSE-KMS 服务端加密**（密钥 KMS 管理、版本化、可轮换）与**生命周期规则**
     （保留期满自动过期）；本地文件仅作无对象存储的私有化降级。
  3) 读取控制：细粒度访问策略（对象/前缀级授权）+ **读取审计**（谁何时读哪条），
     对齐"不是每个人都能看"。
  4) 内容安全：阿里 Green / 腾讯天御以"检测-处置-告警"为主流、不默认全量留底；
     需求方要的"可追溯不当言论"属合规增强 → 实现为**默认关闭**的配置通道。
- 结论：两家均没有"网关默认全量留存用户正文"的产品形态；本需求是**合规扩展**，
  可借鉴的是它们的「事件总线 + 消费目标 + 审计」模式承载事件（即 Kafka 作为我们
  的事件总线），正文密文信封则需自定义协议。

## 3. 需求重构（五条，作为实现基线）

| # | 需求 | 状态/边界建议 |
|---|---|---|
| R1 | 内容留痕：按用户可追溯的请求内容冷存储，加密，最小授权读取 | 需 ADR Accepted；默认关闭；范围=用户消息文本（可扩至双面对话） |
| R2 | Kafka 事件管道：多请求高吞吐投递，平台消费端多进程解耦 | 本 ADR 落地时引入 Kafka（单 broker 起步，topic 按事件族） |
| R3 | 存储目标：**对象存储（S3/OSS/COS 兼容，SSE-KMS 加密）为主流**；本地文件滚动为私有化降级；数据库不建议存正文 | v2 默认=对象存储；P3 保留但默认即此 |
| R4 | 用户身份映射：平台 OAuth user_id → 本网关用户/虚拟 Key（无感） | 前置设计（claims 映射 + 存量用户匹配），平台侧改动到达后接线 |
| R5 | 本系统登录思路不变 | 保持本地 Argon2+session；映射表不替代登录 |

## 4. 架构候选（推荐形态）

```
用户请求 ──网关(启用留痕时,旁路不阻塞)──> 本地缓冲(有界队列 + 落盘暂存 WAL,
   Kafka 不可达时先落本地再重传) ──producer──> Kafka topic content-retention
   (按 user hash 分区保序; 信封: {event_id, tenant_id,
   user_ref(internal uid + 平台 uid 映射), virtual_key_ref, occurred_at,
   sequence, retention_kind, payload(密文, AES-256-GCM; 密钥=部署方 KMS/env,
   非网关热路径)}
      │
      ▼ 平台消费端(多进程, 组内负载均衡)
  持久化目标(配置驱动三选一或组合) = ① 对象存储 SSE-KMS（主，生命周期保留期）
  ② 平台本地文件（按 user 分目录滚动，口述目标）
  ③ 平台侧数据库（口述目标）
  → 受权检索(按 user，读审计)
```

- 网关侧仅在**启用且可配置**时把用户消息正文加密为信封事件；失败语义：默认
  drop+计数（同 usage 队列 F35 语义），"严格模式"可选阻塞（需 ADR 注明取舍）。
- 分区键=用户哈希，保证同一用户时序；不落盘明文。
- 审计：启用/停用/配置变更与读取动作进 admin_audit_events；密文信封的 key 版本化
  （复用 credential 加密 key 体系或独立 retention key，决策点 P5）。
- OAuth 映射（R4）：表 `user_identity_link`（internal_user_id ↔ platform_user_id
  ↔ idp/issuer），在平台 OAuth 校验通过时 upsert；虚拟 Key 事件携带该映射后的
  platform uid（无映射时仅 internal uid）。

## 5. 决策点清单（需 owner/平台拍板）

- P1 红线放宽范围：仅用户文本 / 含代码 / 含模型回复双面对话（建议：仅用户文本起步）。
- P2 默认状态：**默认关闭**（对齐主流"最小留存"），部署配置开启（`MIQROKEY_RETENTION_*`）。
- P3 存储目标与保留期：v2 默认=对象存储 SSE-KMS + 生命周期；**口述目标（平台本地
  文件/数据库）保留为消费端可选输出**（配置驱动，见 §0c），数据库建议只存信封索引
  与元数据、正文进对象存储/文件。
- P4 Kafka 拓扑与容量：标准 Apache Kafka 协议（兼容腾讯 CKafka / 阿里云 Kafka），
  单 broker（KRaft）起步，topic `content-retention` 按 user hash 分区；消费组归平台。
- P5 加密密钥管理：v2 默认=信封加密 + 中心化 KMS（密钥版本化/轮换/授权分离），网关
  只持信封与 key 引用；无 KMS 环境降级为 env 密钥（与 crypto 层同源，授权分离弱化
  需记录）。
- P6 事件协议与投递语义：信封 schema 版本化；at-least-once + 消费端幂等。
- P7 OAuth 映射的触发面（平台接入点/claims 字段），等平台侧"后面会改"的细节。
- P8 带宽/请求量估算（回应 M1）：单客户上限=50 并发流/50 账号；假设每用户消息
  平均 200-2000 字节、每秒活跃请求 ≤ 5-20 条、每请求 1 条事件 → 事件流 ≤
  40KB/s × 系数（含信封与元数据 ≈ ×1.5）→ **≈60KB/s 峰值、日增量 ≈1-3GB**
  （200B×5qps×86400s≈86GB 为极端上界，按实际内容长度加权后取 1-3GB 量级）。
  结论：单 broker Kafka + 少量分区足够；带宽影响可忽略（<1Mbps）；若后续接入
  多租户或更大规模再扩容——据此给平台的容量答复：当前量级对 Kafka/网络无压力，
  预留 topic 分区=用户数无关、按并发×2 即可。
