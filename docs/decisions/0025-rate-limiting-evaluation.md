## 1. 现状

### 1.1 两个治理轴：「配额 ≠ 速率」

| 维度 | 额度治理（配额，**已交付**） | 速率治理（限流，**本文议题，未实现**） |
|---|---|---|
| 语义 | 单位窗口内的**累计量**（用了多少） | 单位时间 / 同时的**瞬时强度**（此刻多猛） |
| 窗口 | 日 / 周 / 月 / 年自然窗口，跨窗口自动恢复 | 秒 / 分钟级滑动窗口，或 in-flight 并发数 |
| 超限动作 | 规则级 opt-in 拒绝：429 `quota_exceeded` + `Retry-After`（ADR-0020 D2，`0020-quota-soft-landing.md:50-54`） | 无任何能力 |
| 对长任务 | 基本无害：窗口以天计，单次长任务打不穿 | **结构性冲突**：长任务的瞬时强度就是它的正常工作形态（见 §2.1） |
| 粒度 | USER / PROJECT 规则（ADR-0020 D3，`0020-quota-soft-landing.md:56-58`） | 未定义 |

一句话：配额管「这个月能用多少」，速率管「此刻能跑多猛」。**把周期配额当成速率限流用，是最容易犯的错**——两者的 `Retry-After` 量级（窗口结束 vs 若干秒）和客户端退避策略完全不同，错误码也不能共用（§3）。

### 1.2 已交付的额度能力（现状基线）

- **语义**：超限的 REJECT 规则 → HTTP **429** + 错误信封 `type=quota_exceeded`，携带 `Retry-After`；Key 不失效，恢复路径为「跨入新窗口」或「管理员提额」；**停用或删除该规则同样立即解除**（`docs/decisions/0020-quota-soft-landing.md:50-54`）。
- **实现形态**：`QuotaEnforcementService`（`@Scheduled` 固定延迟 60s）→ `quota_enforcement` 判定集 → 路由快照 → 网关只读内存映射；**网关热路径零查询、零计数、零算术**（`docs/decisions/0020-quota-soft-landing.md:60-71`）。
- **代码锚点**：`QuotaGate.java:32-35` 抛 `AuthFailureException(HttpStatus.TOO_MANY_REQUESTS, "quota_exceeded", …, retryAfterSeconds)`；准入点在 `ProxyController.java:245`（Key 解析后、读 body 前）。
- **近似语义（已对客户承诺）**：判定集按周期刷新，**不包含评估间隔内新产生的用量**；误差上界 = 一个评估周期（默认 60s）内的放行量 + 快照传播时延；「卡在恰好 100%」不可承诺（`docs/decisions/0020-quota-soft-landing.md:73-79`）。
- **边界原文（本文的直接起点）**：**不做限流**（QPM/令牌桶/速率语义）——配额是**额度治理**，与速率治理（F47）是两件事（`docs/decisions/0020-quota-soft-landing.md:81-87`）。
- **backlog 状态**：F47「QPM/Token 限流（用户级）」= **DECLINED**（`docs/feature-backlog.md:110`）。

### 1.3 速率侧今天有什么：什么都没有，连并发闸也没实现

- `MIQROKEY_MAX_CONCURRENT_STREAMS`（默认 50）是**容量目标**，不是用户限流策略；configuration-reference 明确标注**当前版本未实现**：无并发闸、无对应 `503 CAPACITY_EXHAUSTED`（`docs/configuration-reference.md:148`、`:179`，#733 更正）。本线复核确认代码侧零引用：`grep -rn "MIQROKEY_MAX_CONCURRENT_STREAMS" backend/ deploy/` 无命中。
- 容量过载的**现行为**是自然背压：上游超时 / 缓冲上限（`docs/configuration-reference.md:179`）。
- 因此 F47 行末的「只告警 + 容量 503」（`docs/feature-backlog.md:110`）中，**「容量 503」这半目前并不存在**；「只告警」这半对应下面的 1.4。

### 1.4 观测能力边界（做触发条件判定的前提）

**今天能看见**：

- 逐请求上游状态码落在 `usage_event.upstream_status_code`；`AlertEvaluator` 的 `UPSTREAM_ERROR_RATE` = 滚动 1 小时**非 2xx 占比**，按规则自身租户作用域（`AlertEvaluator.java:132-137`）。
- 告警侧另有 `USAGE_SURGE`：**滚动 1 小时与其前 1 小时的总事件数比**（前窗口为 0 时取哨兵值 100），按规则自身租户作用域、**无用户维度**（`AlertEvaluator.java:39`、`:143`、`:228-241`）。
- 网关请求计数**只有状态类维度**（2xx/3xx/4xx/5xx），且明确禁止 user/key/model/vendor 作指标标签（高基数红线，`GatewayMetricsFilter.java:15-20`、`:30-32`）。
- 用量队列饱和可告警：`USAGE_QUEUE_SATURATION` = 一小时内**丢弃的用量事件数**（`AlertEvaluator.java:149-152`），事实行写在**平台租户**下（`AlertEvaluator.java:42-43`）。告警评估周期默认 **5 分钟**（`AlertEvaluator.java:67`，`miqrokey.alerts.evaluation-interval-ms:300000`）。

**今天看不见**（直接决定 §4 的可行性）：

- **没有 429 专属指标**：`UPSTREAM_ERROR_RATE` 把 429 与 500/502/503/504 混进同一个比值（`AlertEvaluator.java:132-137`）——「上游在限流」与「上游在故障」不可区分；也没有按用户/Key 的维度（维度被高基数红线禁止作指标标签）。
- **队列丢弃无归因**：丢弃计数是全局无标签 gauge / 平台租户事实行（`docs/architecture.md:148`、`AlertEvaluator.java:42-43`），不指向是谁造成的饱和——「谁把共享队列打满」今天答不出来。
- **实例容量吃紧只在症状层可见**：无并发闸（§1.3），只能从上游超时/连接错误等下游症状反推。

### 1.5 一处已存在的文档漂移（本文只登记，不改）

`docs/operations-runbook.md:191` 仍写「**429 只可能来自上游**：本系统**不限流、不阻断**（红线）——网关卡本身不产生 429」。该句在 #684/ADR-0020 落地后已不成立：网关现在会因配额 REJECT 产生 429 `quota_exceeded`（§1.2）。修正登记为后续项（§7.1），本文不顺手改。

## 2. 不做限流的理由与代价

### 2.1 「避免误伤长任务」的实际机制

不是一句口号，而是四条可检验的机制：

1. **长任务的瞬时 token 强度本来就高**：编码类 agent 任务每一轮都要重发上下文，输入 token ≈ O(上下文长度) × 轮次；一次正常的重上下文任务在一分钟内打出很大的 input token 量属常态。分钟级 TPM 阈值只要落在「正常任务峰值」与「滥用」之间，**先被打到的必然是正常任务**。
2. **流的「中途死亡」比「开头拒绝」贵得多**：429 落在任务第 40 分钟时，已经烧掉的时间与上下文无法退回；客户端在窗口内重试同样被拒。用户感知到的是「任务被腰斩」，不是「被限速」。
3. **误伤面是「一个人」而不是「一次请求」**：判定按 USER/PROJECT 而非按 Key（ADR-0020 D3，`0020-quota-soft-landing.md:56-58`）；一个用户通常同时只跑一条流，分钟级窗口命中他时，没有「其他请求」可以退让——省下的是上游额度，付出的是这个人的整条工作流停摆。
4. **共享凭证路径（待核实）**：`virtual_keys.upstream_credential_id` 只有普通索引、**无唯一约束**（`V1__core_tables.sql:445`），同一真实凭证可被多把 Virtual Key 引用。若供应商侧限流按凭证/账号生效，一个用户打满会以**上游 429** 的形式落到共用该凭证的其他人身上。**供应商侧限流作用域未在本线核实**，此为待验证路径而非结论。

### 2.2 不做的代价（什么时候会疼）

1. **单 Key 打满上游时，我们只能被动转发**：供应商按凭证/账号限流时，网关没有「先自我约束」的手段，429 由上游产生；客户端的重试又会放大上游压力。
2. **共享资源没有隔离，且丢弃无归因**：用量写入是有界阻塞队列（默认容量 10000），饱和默认 `DROP`（`docs/architecture.md:148`）；一个用户的爆发造成的丢弃，**不指向产生它的用户**——代价以「别人的用量记录缺失」的形式出现（`AlertEvaluator.java:42-43`、`:149-152`）。
3. **实例容量保护缺位**：并发闸未实现（`docs/configuration-reference.md:179`），过载时所有用户一起退化到自然背压。
4. **没有「减速」这个中间档**：今天只有「记账 / 告警」（无感）与「配额超限拒绝」（到窗口结束一直拒）两端；想在「打满上游」与「完全不拦」之间做柔性减速，没有工具（这正是 §3-B / §3-C 的动机）。

### 2.3 与 P95 首包 30ms 红线的张力

红线：Gateway 自身引入的额外首包延迟 **P95 ≤ 30ms**（`docs/product-requirements.md:128`、`docs/testing-and-acceptance.md:110`、`:117`）。现状的前提是数据面**没有任何实时用量/判定计数器**（`docs/decisions/0019-quota-hard-block-proposal.md:10`；该 ADR 现状态 Superseded，此句落在速率/用量侧——§1.4 的状态类请求计数是另一回事，不构成矛盾）。任何「每请求实时计数」的方案都要在这 30ms 预算里做加法——这是选型的**第一约束**，不是收尾时的优化项。

## 3. 若做，怎么做的选项

四个选项都按五个属性给出：**落点 / 对 P95 30ms 的影响 / 配置粒度 / 与既有 429 信封的错误码区分 / 可回退性**。

### 选项 A：令牌桶速率限流（TPM/RPM）

- **形态**：按 Key 或用户维护每分钟 token 与请求计数（令牌桶 / 固定窗口），超限拒绝。
- **落点**：**沿用 ADR-0020 D4 的「控制面评估 → 判定集 → 快照 → 网关只读」做不到**——速率语义要求秒级反应，而现行形态的评估周期是 60s 且明确「不包含评估间隔内新产生的用量」（`0020-quota-soft-landing.md:73-79`），两者直接冲突。要真做，只能把计数搬到网关热路径（本地计数）或外部状态（Redis）；前者有多实例漂移与重启丢计数（ADR-0020 §3-D 已否决过一次该形态，`0020-quota-soft-landing.md:98`），后者撞 ADR-0005 零中间件（`docs/decisions/0005-no-redis-v1.md`）。
- **对 P95 30ms**：热路径本地原子计数（每请求若干次原子自增 + 一次比较）量级在微秒级，本身不威胁红线；真正的风险是引入外部状态（一次网络 RTT）与逐请求写点数。
- **配置粒度**：Key / USER / PROJECT（与配额同档）。
- **错误码区分**：**必须新码**（如 `rate_limited`），不能复用 `quota_exceeded`——恢复语义不同（秒级 vs 到窗口结束）、`Retry-After` 量级不同、客户端退避策略不同；复用会让客户端学到错误的退避行为。
- **可回退性**：**差**。对外公示过的 TPM/RPM 数字，撤回等于能力倒退；计数机制一旦引入很难摘掉。若限定为「控制面配阈值 + 网关本地计数 + 默认关闭」，机制上可回退，但计数点会留在热路径。

### 选项 B：并发闸（in-flight 流上限）

- **形态**：每 Key/用户最多 N 条同时在飞的流——管的是「同时多少」，不是「每分钟多少」。
- **落点**：网关热路径一个原子计数器，准入 +1、终态（完成 / 上游错误 / 超时 / 客户端取消）−1；与 ADR-0020 的判定集正交，不依赖控制面周期。
- **对 P95 30ms**：一次原子自增 + 比较，纳秒级；**真正的风险是计数泄漏**——少减一次就永久占坑，必须在全部终态路径释放（取消与超时最容易漏）。
- **配置粒度**：Key / USER / PROJECT + 全局兜底。
- **错误码区分**：与 A 同属「临时性拒绝」，同样**不该复用** `quota_exceeded`；且与 #733 预留的实例保护 `503 CAPACITY_EXHAUSTED` 是两件事（容量=实例保护，本项=用户策略）——若两者都做，需两个码，否则无法按码归因「谁拦的」。
- **对长任务**：**比 A 友好**——长任务通常一条流，并发 = 1，不会命中；代价是它**管不住「一条流跑得很猛」**（那是 A 的地盘）。
- **可回退性**：**好**。缺省不限（0 = 不限）、按 Key/用户 opt-in；关掉规则即回到今天。

### 选项 C：排队 + 背压（服务端排队，超限不拒而是等）

- **形态**：超限请求进有界等待队列，等到槽位再转发；队列满才拒。
- **落点**：网关热路径，且**必须非阻塞实现**——WebFlux 事件循环上任何阻塞等待都会毒化整个实例（`docs/architecture.md` §6 的超时体系也是围绕非阻塞设计的）。
- **对 P95 30ms**：未命中队列的请求无影响；但**红线的口径会变模糊**——排队一旦发生，首包必然远超 30ms。排队时长算不算「网关自身引入的延迟」需要 owner 定口径，否则红线失去意义（本文不替 owner 定义）。
- **额外代价**：排队期间客户端超时与整体硬截止（默认 10 分钟，自第一次尝试起计时，`docs/architecture.md:157`）**已经在走**——排队越久，真正可用的推理预算越少；流式请求排队还会占住内存。
- **配置粒度**：同 A/B，另需队列容量与最大等待时长。
- **错误码区分**：只有「队列满」之后的拒绝涉及错误码，同样需要独立码。
- **可回退性**：中（队列机制本身会留下）。
- **对标提示**：issue 提到阿里「服务端排队」，**本仓无该记录、本线未核实**（§1.6）。

### 选项 D：只告警，不阻断（速率观测 + 阈值告警）

- **形态**：把「上游 429 频率 / 单 Key 用量突增」做成**可归因的信号** + 告警规则，超阈值只发 Webhook；**不做任何拒绝**。
- **落点**：完全在控制面，复用 `AlertEvaluator` 的滚动小时 SQL 与 `alert_rules` 框架（`AlertEvaluator.java:124-157`）——**热路径零改动、零延迟**。
- **对 P95 30ms**：**无影响**（不进热路径）。
- **配置粒度**：规则级（租户/scope）；SQL 里可以按 user/key 分组——**告警不是指标标签**，不违反高基数红线（`GatewayMetricsFilter.java:15-20` 约束的是 Prometheus 标签）。
- **错误码区分**：不产生拒绝，无错误码问题。
- **可回退性**：**完美**（没有引入新机制，只有一条新规则）。
- **代价**：它只解决「有没有据可依」，不解决「打满上游时谁能拦住」。且今天的 `UPSTREAM_ERROR_RATE` 把 429 与 5xx 混在一起（`AlertEvaluator.java:132-137`），要做 D 至少要补一个 429 细分（按 `upstream_status_code = 429` 分组或新增规则类型），属小改动。

### 选项比较

| | 落点 | P95 30ms | 配置粒度 | 错误码 | 可回退性 | 能挡住「单 Key 打满上游」吗 |
|---|---|---|---|---|---|---|
| A 令牌桶 TPM/RPM | 网关热路径（+可能外部状态） | 本地计数微秒级；外部状态 RTT 不可接受 | Key/USER/PROJECT | 必须新码 | 差 | 能（但误伤长任务） |
| B 并发闸 | 网关热路径（一个原子计数器） | 纳秒级；泄漏风险在实现不在延迟 | Key/USER/PROJECT + 全局 | 必须新码（≠ 容量 503） | 好 | 部分（管不住单流打满） |
| C 排队 + 背压 | 网关热路径（非阻塞） | 口径需 owner 重新定义 | 同上 + 容量/等待上限 | 队列满才涉及，需独立码 | 中 | 部分（延迟换平滑） |
| D 只告警 | 控制面（零热路径改动） | **无影响** | 规则级 | 不涉及 | 完美 | 不能 |

### 本 ADR 的建议（供 owner 拍板，不构成决定）

1. **第一期做 D**：把 429 观测细分 + 单 Key 速率信号补齐——零热路径风险、零不可回退决策，且它恰好产出 §4 判定所需的**证据**。今天没有这份证据，任何「做不做」的表态都仍然是口号。
2. **若 §4 的信号被命中，优先评估 B 而不是 A**：并发闸对长任务的结构性误伤更小（长任务并发通常为 1），同时兑现 #733 尚未实现的容量语义；A（TPM/RPM）只在「上游按凭证限流且 429 实测频发、B 不足以缓解」时才评估。
3. **无论选哪条，都不采用**「请求路径实时查库 / 查 Redis / 数据面增量计数」形态（§6）。

## 4. 触发条件（什么信号下重新评估 / 开启）

| # | 信号 | 今天能否观测 | 说明 |
|---|---|---|---|
| 1 | 上游 429 频发（按用户/Key） | **间接**：`upstream_status_code` 有值，但只有「非 2xx 占比」（`AlertEvaluator.java:132-137`），无 429 切片、无用户维度 | 需先做 §3-D 的细分 |
| 2 | 单用户/单 Key 用量占比失衡 | 部分：用量汇总支持 `user`/`model`/`month` 等分组（`docs/api-contract.md:235`）；告警侧有 `USAGE_SURGE`，但它是**租户级总量比**、无用户维度（`AlertEvaluator.java:39`、`:228-241`） | 缺「单用户占比」类信号，需新增规则类型 |
| 3 | 共享池劣化（用量事件被丢弃） | 能看见丢弃数，**不能归因**（`AlertEvaluator.java:42-43`、`:149-152`） | 归因是 §7.4 |
| 4 | 实例容量吃紧 | 仅症状层（上游超时/连接错误），无并发闸（`docs/configuration-reference.md:179`） | 与 #733 同源 |
| 5 | 外部/合同侧要求 | 不可自动观测 | 人工输入 |

**建议判定门槛（供拍板，非既定）**：

- 任一滚动 7 天窗口内，上游 429 **≥ N 次**且影响 **≥ 2 个不同用户** → 启动 A/B 的立项评估（N 建议 50，依据是「单次偶发」与「系统性打满」的分界，可由 owner 调整）；
- 或单用户单日用量占比 **≥ 40%** 且同窗口出现用量队列丢弃 → 优先评估 B（并发闸）；
- 或并发流数持续贴近 50 的容量目标并出现上游超时 → 按 #733 的容量语义处理（那是保护实例，不是用户限流）。

**若长期不满足**：维持 ADR-0020 D6「不做速率限流」，本文即作为「不做的决策记录」收口（对应 issue #706 的验收标准第 3 条），并按本文 §1.4 的观测能力年度复核。

## 5. 需要 owner 回答的问题（3–5 条，带推荐答案）

1. **本期是否立项做速率限流？**
   推荐：**不立项**，先做 §3-D 的观测细分（可逆、零热路径风险），把 §4 的信号变成可判定；速率限流本体留到触发条件命中。
2. **若开启，与周期配额是什么关系——互斥还是叠加？**
   推荐：**叠加，但错误码与 `Retry-After` 语义必须分离**。配额管额度、限流管强度，两者正交；混用错误码会让客户端学到错误的退避策略（§3-A）。
3. **粒度与默认值？**
   推荐：**不设全局默认**——与 ADR-0020「规则级 opt-in、默认零回归」（`0020-quota-soft-landing.md:46-48`）保持一致；新增能力默认关闭，按 Key/用户显式开启。
4. **是否接受为了秒级计数在数据面开一个口子（本地计数，接受多实例漂移与重启丢计数）？**
   推荐：**不接受**。P95 30ms 红线与 50 并发目标不值得为此开洞；若必须做，先做并发闸（热路径一次原子操作），而不是把 TPM 计数塞进热路径。
5. **对外表述如何统一？**
   推荐：对外只说「当前明确不做速率限流，原因是避免误伤长任务；开启的判定条件见 ADR-0025 §4」——把可被追问的问题从「无据」变成「有据」，本轮不改 PPT 的能力承诺。

## 6. 被否的替代方案

| 方案 | 否决理由 |
|---|---|
| 请求路径实时查库 / 查 Redis 计数 | 违反热路径零查询与 ADR-0005 零中间件，把数据面可用性绑到外部状态；ADR-0020 §3-C 已否过一次（`0020-quota-soft-landing.md:97`） |
| 数据面本地 `usedSinceLoad` 累加（ADR-0019 草案形态） | ADR-0020 §3-D 已否：快照需携带逐规则计数器、每请求按规则累加、多实例近似漂移、重启丢计数，收益不足以覆盖复杂度（`0020-quota-soft-landing.md:98`） |
| 复用 `quota_exceeded` 承载速率拒绝 | 恢复语义与客户端退避策略不同（秒级 vs 窗口级），混用会让客户端学到错误行为，也让 429 归因失去区分度 |
| 用 #733 预留的 `CAPACITY_EXHAUSTED` 承载用户级限流 | 语义不同：那是**实例保护**，这里是**用户策略**；混用后无法按码归因「谁拦的」 |
| 照搬厂商默认阈值 | 我们的负载形态是编码类长任务（单任务瞬时 token 高），厂商标定面向问答式流量；照搬必然误伤（§2.1） |
