# ADR-0020：配额软着陆——REJECT 规则超限拒绝请求（429）

- 日期：2026-09-16
- 状态：**Accepted**——产品负责人（用户）2026-09-16 明确拍板「软着陆：拒绝请求」，否决「超限自动禁用 Key」。本 ADR **采纳 ADR-0019（Proposed 草案）的选项 B（规则级 opt-in 拒绝）并给出落地形态**；ADR-0019 保留为提案记录（状态标注为已被本 ADR 采纳）。
- 效力：本 ADR 修订 CLAUDE.md §2 产品决策条目「不限流、不因预算阻断，只做 Webhook 告警」——修订为「默认只告警；标记为 REJECT 的配额规则在超限后拒绝请求（429），其余仍不限流、不做预算熔断」。
- 关联：issue #684；[ADR-0019](0019-quota-hard-block-proposal.md)（提案）；[ADR-0002](0002-transparent-proxy.md)（透明代理红线：本议题不改写请求内容，仅准入判定）；[ADR-0005](0005-no-redis-v1.md)（不引 Redis——本形态不需要）；api-contract §5.19；database-schema（`quota_rules.action`、`quota_enforcement`，V59）；configuration-reference（`MIQROKEY_QUOTA_ENFORCEMENT_*`）；腾讯云 AI 网关「配额管理」（owner 2026-09-16 样本：「当配额使用达到 100% 时，系统将自动拒绝新的请求，直到配额重置或增加限额」）。
- 触发事件：2026-09-15/16 外部机器持续使用某把 Virtual Key 两天——配额水位与告警都在，但**请求该过还过**；失控用量只被"记录"、不被"刹住"。

---

## 1. 背景

### 1.1 原决策与它的语境

CLAUDE.md §2 的「不限流、不因预算阻断，只做 Webhook 告警」写于首版语境：单租户私有化、50 账号、单人运营。当时的判断是——阻断的收益（省下的钱）配不上它的风险（误伤可用性、把运维问题变成业务中断）。

### 1.2 发生了什么变化

1. **配额治理面已经建全**：规则（V23）、读时水位、四档状态（NORMAL/WARNING/NEAR_LIMIT/EXCEEDED，V58）、告警 Webhook、默认模板、自助可见——唯独**没有"执行"**。一个只会记账不会刹车的大门，在 Key 泄漏/失控时等于没有。
2. **事件给出反例**：Key 被外部机器持续调用两天无人察觉。事后复盘的第一性问题不是"告警规则缺默认值"，而是"**即使水位 100%，系统也不会做任何事**"。
3. **owner 样本（腾讯）**：腾讯 AI 网关配额管理把「超限处理=拒绝请求」作为标准档位，并明确「直到配额重置或增加限额」——拒绝是**可恢复**的临时状态，不是处罚。

### 1.3 与 ADR-0019 的关系

ADR-0019 是并行的配额扩维批次（#683/#686）留下的**提案**，列出三个决策点与三个未决问题（是否立项 / 首版范围 / 429 vs 403）。本 ADR 是 owner 拍板后的落地记录：

- 决策点 1：选 **B（规则级 opt-in）**——默认行为零回归，反转范围最小；
- 决策点 2：**采纳其挂点（Key 解析后、转发前）**，但**不采纳其"数据面 usedSinceLoad 计数"形态**（见 D4 与 §3）；
- 未决问题：① 立项=是；② 首版范围=USER+PROJECT × 全部三种指标（TOKENS/REQUESTS/COST），不缩到 TOKENS——判定复用同一份水位，缩范围不省成本；③ 状态码=**429**（窗口后可重试，语义正确）。

## 2. 决策

### D1. 规则级超限动作：`action ∈ {ALERT, REJECT}`，默认 `ALERT`

`quota_rules` 增列 `action`（V59，`ALERT|REJECT`，默认 `ALERT`）。存量规则、默认模板复制出的规则、未携带该字段的旧客户端一律保持 `ALERT`——**默认行为与今天完全一致**。一个 scope 命中多条 REJECT 规则时，任一超限即拒。

### D2. 软着陆语义（对齐腾讯）

- 超限的 REJECT 规则覆盖的用户/项目，其请求被网关拒绝：HTTP **429** + 标准错误信封（`type=quota_exceeded`），文案注明"配额重置或提高限额后自动恢复"；响应携带 **`Retry-After`**（秒）= 判定集里该作用域最早可自愈的窗口结束时刻（同一作用域被多条规则拦截时取最早）——AI 客户端与重试库普遍按此退避，避免"被拒后继续打"。
- **Key 不失效、不自动禁用、不删数据**；`virtual_keys.status` 不被本机制触碰。
- 恢复路径只有两条，且都无需人工干预数据面：**跨入新窗口**（评估器下一轮自然清除判定）或**管理员提高限额**（同上）。停用/删除该规则同样立即解除。

### D3. 作用域与判定粒度

USER / PROJECT（既有两档）。判定按 **scope** 而非按 Key：同一用户/项目下的其余 Key 一并生效——这与"配额属于谁"的语义一致（配额挂在用户/项目上，不是挂在某把 Key 上）。

### D4. 实现形态：控制面评估 → 判定集 → 路由快照 → 网关只读内存集合

```
QuotaEnforcementService（@Scheduled 固定延迟 60s，initialDelay 45s）
  → 遍历 ACTIVE REJECT 规则，经 QuotaWatermarks 计算当期水位（与「配额规则」页同一份计算）
  → 超限者写入 quota_enforcement（整体替换）
  → 判定集变化时才 RouteRefreshPublisher.publishChanged()
  → 网关快照携带 quotaBlockedUsers / quotaBlockedProjects（作用域 → 最早窗口结束）
  → 准入处（ProxyController / ModelsController，Key 解析后）查内存映射 → 429 + Retry-After
```

**网关热路径零查询、零计数、零算术**——只做两次 `Map.get`。判定与页面水位共用 `QuotaWatermarks`，两者永不打架。

### D5. 近似语义（显式承诺，与 ADR-0019 §决策点 2 一致）

判定集按周期刷新，**不包含评估间隔内新产生的用量**：

- 误差上界 = 一个评估周期（默认 60s）内的放行量 + 快照传播时延；
- 因此"卡在恰好 100%"不可承诺，额度可能被超出一个周期的量（与腾讯"配额使用情况小时级更新"同类，属本类系统的常态）；
- 页面与网关可能在一个周期内不一致（页面已 100%、网关尚未生效，或反之）——以"最多晚一个周期"为准，不额外承诺强一致。

### D6. 边界（本次不做）

- **不做限流**（QPM/令牌桶/速率语义）——配额是**额度治理**，与速率治理（F47）是两件事；
- **不做预算硬熔断**（`budget` 表仍只告警，不在本 ADR 范围）；
- **不做消费者组维度**（无组实体，维持 #683 结论）；
- **MCP 面不在首版**（MCP 的调用方是 API 消费者而非 Virtual Key，配额作用域未覆盖该维度）；
- 不引入 Redis 或任何热路径外部状态（ADR-0005 不变）。

## 3. 被否的替代方案

| 方案 | 否决理由 |
|---|---|
| A. 维持 alerting-only | 事件已证否：失控 Key 需要的是刹车，不是又一条告警 |
| B. 超限自动**禁用 Key** | 不可逆、需人工恢复、误伤面大（一把 Key 停掉一个人的全部工作）；owner 明确否决 |
| C. 请求路径实时查库/查 Redis 计数 | 违反热路径零查询与 ADR-0005；把数据面可用性绑到外部状态 |
| D. 数据面本地 `usedSinceLoad` 累加计数（ADR-0019 原草案形态） | 判定更"准"约一个周期，但要付出：快照携带逐规则计数器、每请求按规则累加（含 COST 的逐请求估价）、多实例并发下的近似漂移、重启丢失计数。**收益不足以覆盖复杂度**；保留为后续精化选项——若确需更紧的卡口，可在本 ADR 的判定集之上叠加数据面增量计数，**对外语义（D2/D5）不变** |
| E. 网关按 30s 轮询自己算 | 与控制系统职责重叠、每实例重复聚合；快照通道已存在且是既有唯一事实来源 |

## 4. 后果

**数据面**：快照新增两个 `Map<UUID, Instant>`（用户→最早窗口结束、项目→同）；准入处新增一次判定（解析后、读 body 前）；MCP/管理面不受影响。快照结构向后兼容（空映射=不判定）。

**控制面**：`QuotaEnforcementService` 每 60s 一轮（可用 `MIQROKEY_QUOTA_ENFORCEMENT_INTERVAL_MS` 调整）；单规则计算异常被隔离（保留该规则上一轮判定，不清空整个判定集）；判定集未变化时零写入、零广播。

**数据库**：V59——`quota_rules.action` + `quota_enforcement`（rule_id PK、tenant FK CASCADE、scope_type/scope_id、metric/period 存档、`window_end`、blocked_at）。`window_end` 是评估时刻该规则窗口的结束时间，快照按作用域取最早值 → 429 的 `Retry-After`。判定集是**可重建的派生数据**：清空该表只会让下一次评估重新写入。

**API/前端**：`UpsertQuotaRuleRequest.action`（可选，缺省 ALERT）、`QuotaRuleView.action`（回显）；配额规则页表单增「超限动作」选择、列表增列；「我的配额」面板标注该规则的动作。审计摘要含 `action`。

**风险与缓解**：

- *误拒*：默认 ALERT、opt-in 才拒；DISABLED 规则不产生判定；评估器故障时保留上一轮判定（宁可维持现状也不静默放行）；
- *静默失效*：若评估器长期不运行，判定集会停留在旧状态——下一轮成功评估即自愈；本轮不做额外的健康探测（记录为后续项）；
- *观感差异*：见 D5，已写入 api-contract；页面与网关都不承诺逐秒一致。

## 5. 未纳入（记录为后续项）

1. `QUOTA_REJECTED` 告警事件（拒绝时产生一条 alert_rule 事件）——本 ADR 不引入新事件类型（`Retry-After` 已提供客户端侧退避信号）；
2. 拒绝的**准入日志**（当前 429 只进网关日志与保留日志的错误路径，不写 usage_event——被拒请求不产生用量事件是既有口径）；
3. ADR-0019 §决策点 2 提及的 `quota_counters` 表与数据面增量计数（见 §3-D）；
4. 评估器停滞的健康探测/自监控。
